# Project Conventions

Enforce on EVERY change — and when fixing a gap, sweep the whole class of it project-wide, not just the reported instance.

**Organization, everywhere (owner, 2026-10-01 — "store change kar k organization kar du? ... hospital aur education like school aur bhi dusre institue ko bhi sell kar saku", then "ab haar jagha organization kardo, Database mein aur jaha jaha bhi store use huwa ha usko organization kardo"):** the tenant is an **organization** in every word a person reads and in the code and the database alike — tables and columns (`organizations`, `organization_user`, `organization_id`), models and services (`Organization`, `OrganizationTeam`, `OrganizationStorage`), routes and URLs (`/organizations`, `/settings/organization`, `organization.switch`), the session key (`current_organization_id`), permission names (`organization-view` …), logged actions (`organization.created`), `dusk` names and JSON keys. A new word, name or key says organization, never store or shop. What stays "store": the word meaning *save* — a resource's `store` action and its route name (`media.store`), the `{resource}-store` create permissions (`media-store`, and `organization-store` for creating an organization), `StoreMediaRequest`, `MediaStorage::store`, Laravel's `storeAs` and cache store, Alpine's `$store`, the player's local-storage helper. The databases that existed were renamed in place on 2026-10-01 (tables, columns, indexes, keys, the four permissions, the logged actions and the `Organization` subject), and the migrations have said organization from their first line since (see **Migrations** below). `OrganizationWordsTest` fails on "store" or "shop" anywhere a page lets a person read it, and `MigrationsTest` on a table, column, index or migration file named after a store — **a new page joins the first one's lists.**

**Migrations — one file per table (owner, 2026-10-01 — "itni sari migration ki file ban gae ha, isko kum kar sakte ha? har table ki ek, jese hum fresh kaam shuru karte ha"):** `database/migrations` is Laravel's own three files (users with password resets and sessions, cache, jobs), one `create_{table}_table` file for every other table, in an order the foreign keys allow, and `2026_10_01_202300_insert_permissions_and_starter_roles` — 26 files that build exactly what the forty before them had built (proved table by table on MySQL: against a build from the old files, against the live database and against the owner's own). A database the old files built has every table already, so **each file leaves a table that is there alone** (`Schema::hasTable` first; the last file skips a catalogue that exists, and forgets the old files' rows in `migrations`). Which is why **a file here is never edited to change a database that exists — that database would skip it: a new column, index, table or permission is a NEW migration**, reversible, and a new table gets a `create_{table}_table` file of its own. `activity_logs` partitions itself by year on MySQL inside its own file. The first change since is one: `2026_10_02_100000_put_the_time_on_the_schedule_rule` (the dayparts go, see **Schedules**) — the two daypart tables' create files stay beside it until every database has run it, as the files it follows did. `MigrationsTest` holds it: a file per table, nothing named after a store, every file harmless on a database that has its tables, the catalogue kept, and the whole set rolled back and forward. A dump taken before 2026-10-01 22:39 UTC still says `stores`: it is brought forward with the code of commit `0eb3740`, which carries the rename, before any later one (deploy/README.md).

**Authorization model — the organization (docs/ORGANIZATION-SPEC.md is the source of truth):** power comes from **membership** alone — an `organization_user` row `(user_id, organization_id, role_id)`, one role per person per organization — never from who created whom. Nobody owns an account: there is no `users.created_by`, no admin sets or knows another person's password, and a person's name, phone, email and password change only from their own Profile or "forgot password". Two tiers, mutually exclusive — a platform account is never an organization member and an organization member never holds a platform role (accepting an invitation, the owner email of a new organization and platform invitations all refuse the other tier):
- **Platform** = a membership on the sentinel `organization_id = 0` holding a global role (`User::globalRole()`). It works above the organizations — every organization, every account — limited to its role's permissions. **Super-Admin** is the role named `Super-Admin` there. **A super admin holds every permission** (owner's rule, 2026-09-16: "sab matlab sab"): a `Gate::before` in `AppServiceProvider` answers yes to every permission check whatever the role's rows say — a permission made later, or renamed, included. It answers permission checks only: rules that are not permissions still stand (the primary's protection, Super-Admin never changed and the Owner role never deleted, an organization's last Owner, a super admin never deleting themselves), and `network-ads-toggle` — a place ("inside an organization, logged in as one of its people"), not a permission — keeps its own test. Only super admins make the organization roles and the platform roles (see **Roles**), look after every organization's custom roles from the platform (the Roles page lists them in a card of their own), put anybody in any organization with a role, change that role or take them out (Users page → **Organizations**, owner's rule 2026-09-17: `UserController::organizationAccess`/`assignToOrganization`/`changeOrganizationRole`/`removeFromOrganization` — straight in, nobody invited; a role that organization has; never a platform account; the organization keeps an Owner; taking someone out asks for the password), invite platform staff, remove a platform role, "Log in as" and reach the permission catalogue. **"Log in as"** keeps two session keys (`ImpersonateController::SESSION_KEYS`: who to return to, and whom they view as), written after the impersonation's own login; every sign-in clears them (a `Login` listener in `AppServiceProvider`) and "stop" works only for the account being viewed as — a session whose impersonated account was deleted mid-way once handed the super admin to the next person who signed in on that browser. The **primary** super admin (`User::primarySuperAdminId()`, the first Super-Admin membership) alone may take Super-Admin from someone or delete a super admin account, and nobody may act on the primary.
- **Organization** = memberships in real organizations. Permissions are read against the membership of `session('current_organization_id')` (`User::contextPermissionNames()`; a platform role always wins over a stale organization left in the session). Holding a permission in organization A grants nothing in organization B. An organization's role may also carry the platform permissions that can work inside one organization, and there they reach that organization alone (see **Platform permissions**). **An organization the platform pauses** (its Active switch off, `organizations.is_active`; owner, 2026-09-30) is closed to its own people: `EnsureOrganizationIsActive` (`organization.active`, on every route of the signed-in panel and on the uploads) sends a page to the dashboard, which says "{organization} is paused" (`dashboard/partials/paused.blade.php`), and refuses a request a page makes with the same words (403); their role there grants nothing meanwhile (`User::pausedOrganization()` inside `contextPermissionNames`), so no page offers what would be refused; switching to another of their organizations (`organization.switch`), leaving it and their own profile stay open. "Log In As" one of them shows the same page. The platform is never stopped by it — it looks after the organization and turns it back on from the Organizations page ("Off pauses the organization") — and the organization's screens keep playing: the device API is not behind it (the owner has not asked for a paused organization's televisions to stop). Pausing and turning back on are logged as `organization.paused`/`organization.resumed`; an organization's own people can never switch it (Settings → Organizations ignores `is_active`). A new signed-in route joins that group — `PausedOrganizationAttackTest` walks every one.

**A role does not matter — its permissions do (owner's rule, 2026-09-17: "role matter nahi karta, permission matter karta ha"):** whatever a role is called, what its holders may do is exactly what its permissions allow, and a page shows exactly those buttons and links. No rule asks "is this person an Owner?" to allow an action; the Owner role's only special standing is below. The super admin decides who holds which permission and takes care that a role gets nothing that could break an organization.

**Roles — no built-in roles but Super-Admin (owner's rules, 2026-09-17):** the super admin makes a role and says what it is for. **Organization roles** (`is_global = false`, `organization_id` NULL) are made on the platform's Roles page with "Organization role" and are offered in EVERY organization; the super admin renames them and changes what they allow (every organization at once, `RoleController::update`); inside an organization they are read-only. **Delete** is offered on every role but Super-Admin and the Owner role — a role somebody still holds is refused with **"Please unassign {role} from everyone first: {n} person still holds it."** (the Roles page says it as a toast at once, before any password; `RoleController::destroy` refuses it again with a 422). **The Owner role** is the organization role marked `roles.key = 'owner'` (`Role::OWNER`, `Role::owner()`, `Role::isOwner()` — never found by its name): its holders are the organization's owners — an organization may have several (partners) — "at least one Owner" counts it, public signup, owner invitations and Create organization give it, and an organization changes hands by giving it on the Members page. It is renamed and changed like any organization role but never deleted. **Platform** roles (`is_global = true`) are made with "Platform role", for the team above the organizations. What a role is for is fixed once it exists. **Custom** roles (`organization_id` = the organization) are an organization's own, made on its Roles page: any member holding `role-update`/`role-destroy` manages them within reach whoever created them, a super admin manages every one from the platform, they survive their creator, and one still held cannot be deleted. `Role::STARTERS` (Owner, Admin, Staff, Viewer — keys `owner`/`admin`/`staff`/`viewer`) is only where an installation begins: one migration inserts the permission catalogue and all four roles (`2026_10_01_202300_insert_permissions_and_starter_roles`) and the seeder only puts the Owner role back should it be missing — neither ever touches an existing role, so a re-seed cannot undo the super admin's changes or bring back a role they deleted; a starter key gives no power. Owner and Admin start with every organization permission and View Organizations; Delete Organizations starts with the Owner role alone. A name must be new to every list the role is shown in (`RoleController::validated`), compared with accents, case, spacing and punctuation folded away: an organization role against every organization role and every organization's custom roles (it is listed in all of them), a custom role against its organization's list, a platform role against the platform roles, and nothing may be named like Super-Admin. A role of another organization is never usable here (`Role::availableInOrganization`: 422 on `role_id` when inviting, assigning or changing a role, 404 on the Roles endpoints). (The migrations that upgraded the owner's own database to this model — the people conversion, the merge of same-named organization roles, the organization-transfer permission and its removal — were squashed away on 2026-09-17, and every change since on 2026-10-01: `database/migrations` builds the final schema and the starter data directly, one file per table — see **Migrations**.) **The Super-Admin anchor is the exact name compared in PHP (`Role::SUPER_ADMIN`, `Role::superAdminId()`, `User::isSuperAdmin()`), never a `WHERE name = 'Super-Admin'`:** MySQL's `utf8mb4_0900_ai_ci` collation reads "Súper-Admin" as that very name, so a SQL comparison let a look-alike custom role make every holder a super admin.

**Hierarchy (one place: `App\Services\OrganizationTeam`):** to **assign** a role (invite, change role) it must be available in the organization and the actor must hold every permission of it in this organization (`mayAssign`). To **manage** an existing member (change role, remove) it must not be yourself and the actor must hold every permission of the member's current role (`mayManage`). Both compare permissions only (`roleIsWithinReach`) — the Owner role is given and managed like any other, by whoever holds everything it allows (owner's choice, 2026-09-17). Because an Owner can be reached by somebody who is not one, the last-Owner rule below is checked on its own in every change or removal of a member (Members page `MemberController::update`/`refuseTheLastOwner`, Users → Organizations), and a row never offers it (`can_manage` is false on an organization's only Owner). **At least one Owner, always:** the last Owner cannot be demoted, removed, leave, or delete their account — and every change that could break that is decided under the organization row's lock (`OrganizationTeam::changeTeam`, `lockOrganizationsOwnedBy`), reading the owners INSIDE the lock, so two co-owners acting at the same moment cannot both pass. **Leaving** is open to every member: from the Members page, from "Your organizations" on Settings → Organizations, or — without View Organizations where they work — from "Your organizations" on the profile (`ProfileController::leaveOrganization` returns to the page it came from). An organization changes hands **on the Members page** (owner's rule, 2026-09-17 — there is no Transfer Ownership and no `organization-transfer` permission any more): whoever holds everything the Owner role allows gives it to another member with Change role, and the new Owner may then change the first one's role — the last-Owner rule keeps the organization from being left without one in between. The server sends what each row allows (`can_manage`, `assignable_roles`, `can`), so a page never offers what the controller would refuse — and the controller checks it again regardless.

**How people enter (nobody is created by somebody else):**
- **Public signup** (`/register`, routes/auth.php): a customer creates their account and their organization in one form and becomes its **Owner** — server-chosen (`Role::owner()`), never client input — and confirms their email before the panel opens (see **Email verification** below). **The form keeps robots out** (owner, 2026-09-30: made-up names signed up on the live site all day, each sending a confirmation email to somebody's real address): `<x-auth.robot-trap>` carries a `display:none` field no person meets (`website`) and the sealed (encrypted) moment the form was opened, and `RegisteredUserController::looksLikeARobot` sends the form back with "Please try again." — nothing written, logged or emailed — when the field is filled or, while `signage.signup_min_seconds` is above nought (3 by default, none under the test suites), the form came back sooner than that, with no sealed moment, a forged one or one older than `signup_form_lifetime_seconds` (two hours); `SignupRobotAttackTest` holds it. A robot that gets past both makes an account nobody confirms, which the 7-day prune takes.
- **Invitation** — from an organization's Members page (`member-invite`); from the platform when it creates an organization for a customer (`organization-store`: the owner's email gets an Owner invitation) or gives an ownerless organization an owner; and for platform staff (super admins). The 64-character token lives only in the email — the database keeps its SHA-256 hash (`invitations.token_hash`) — the link lasts `Invitation::LIFETIME_DAYS` (7), Resend rotates the token and Revoke deletes it. The link's page (`InvitationResponseController`) creates the account when none exists (marked verified: opening the link proved the inbox) and otherwise makes the person sign in first — **the link alone never logs anybody in** — and tells a person signed in with another email so. Accepting and registering take the invitation row under a lock, so a double submit or a second tab never uses one link twice. The email goes out through `Invitation::sendLink()`, which reports a refusing mail server instead of throwing — the response says `email_sent: false` and the page shows it as an error, while the invitation stands for Resend. On the platform, **"Invite owner" is offered only for an organization with no Owner** (owner's rule, 2026-09-17): the row's `can.invite_owner` needs `organization-store` and an `owners_count` of 0, and `OrganizationController::inviteOwner` refuses an organization that has one (422, "{organization} already has an Owner.") — more Owners come from the organization's own Members page, or Users → Organizations. A member of that organization is made Owner at once; anybody else is invited. The same address again sends a fresh link (expired or not), and a different address — or a member made Owner — retires the earlier owner invitations (`retireOwnerInvitations`), so a mistyped email stops working. Only the primary super admin invites a new super admin (the one who can also take it away). Both sides are throttled by named limiters (`invitations`, `invitation-response`). The dashboard deliberately lists no invitations to accept: only the emailed link may accept — every account made before email verification was marked confirmed without any proof of its inbox.
- **Email verification** (owner's rules, 2026-09-29 — "we will do email verification when anyone will create account", "no aliases, delete after 7 days"): signup sends a signed link (`VerifyEmailNotification`, `auth.verification.expire` minutes, naming the account by id and the address by `sha1`), and until it is opened the account stands behind `verified`: every page sends it to "Check your inbox" (`verification.notice`, a JSON request gets 403), and only its profile, the verification pages and links, accepting an invitation, its password, sign out and "stop" after "Log in as" stay open — `HttpSurfaceSweepTest` pins that list, so a new signed-in route outside `verified` fails until it is added on purpose. A link opens nothing by itself (the account must be signed in) and a wrong one says why on the page it lands on (`EmailVerificationController::whyNot`). **One account per address, compared as typed** (no folding of dots or `+tags`). What came to the inbox confirms it too: accepting an invitation, and completing a password reset — which also ends every session of the account (`User::endEverySession`), so somebody who signed up with another person's address and kept a session open loses it the moment that person resets the password. A confirmed account's changed email waits in `users.pending_email` until the link sent to the NEW address is opened (`email.confirm`, `ConfirmNewEmailNotification`): the old one stands meanwhile, the change can be sent again or given up, and an address another account took in between is refused, never taken; an account not yet confirmed simply corrects its address, and the link goes to the new one. **Every email that confirms an address draws on one budget** — the signup's, "Send the link again" on either page, and a new address typed on the profile: 3 a minute and 20 an hour per account (`User::LINKS_PER_ACCOUNT`) and 30 an hour per visitor's IP across every account they make (`LINKS_PER_VISITOR`), counted inside `User::sendALink`, so no door can skip it; the profile asks `linkRefusal()` BEFORE it saves a new address, so a refusal leaves the account as it was ("Too many emails asked for. Try again in …", under the field or in the page's box — never a bare 429). And the two confirmation emails carry no text anybody typed but the recipient's own address — no name: they go to whatever address a visitor types, and a name is where signup spam puts its words. Opening links is limited by the named `verification-link`. **An account never confirmed goes after `User::UNVERIFIED_DAYS` (7) days** with its organization (`accounts:prune-unverified`, daily at 03:15 by the server's existing scheduler cron): only when every organization of theirs is theirs alone and empty (`WHAT_AN_ORGANIZATION_HOLDS`), decided under the organization rows' lock and then the person's own, and the run names every account it keeps. The migration that brought the rule marked every account made before it as confirmed (one exact stamp, which its `down()` undoes), so nobody on the live site was locked out. The Profile's email status keys are in `components/toasts.blade.php`'s list, so none becomes a toast of its raw key.
- **No API:** this is a web-only app — there is no `routes/api.php` and no token API, by owner decision (a half-built mobile login was deleted 2026-09-03). Do not add API routes without explicit instruction; any future API needs validation, throttling, and tests from day one.

**Visibility & scoping:** inside an organization, `member-view` shows **every** member of the current organization (the viewer marked "You") and its pending invitations — never anybody outside it, never a platform account — an organization's people have no Accounts page of their own, the accounts pages are the platform's alone (`can:global-tier`, owner's rule 2026-09-17); `organization-view` on an organization's role opens the Organizations tab of Settings for the organization the person works in. On the platform a super admin sees every account, and a platform user holding `user-view` sees organization accounts only. Every WRITE endpoint resolves its target inside where the actor stands: `ResolvesCurrentOrganization::currentOrganization()` (404 unless the session's organization exists and the actor is a member of it), `OrganizationTeam::roleOf()` (404 for somebody who is not a member), an invitation's `organization_id` against the current organization, a role through `Role::availableInOrganization`. Route middleware (`can:`) alone is NOT enough, and an id out of scope answers 404.

**Per-organization isolation (the organization is the wall):** whatever a member creates belongs to the organization they created it in — stamped from `session('current_organization_id')` on create — and every read and write of it lands in that same organization. With no organization selected an organization member sees nothing at all (an empty scope, not an unfiltered list). When adding any new organization-scoped entity: stamp it with the organization, add the same walls, and add it to `Organization::purgeContents()`, all in the same commit.

**Media library (organization inventory, not personal property):** a library belongs to an organization, or to the platform (docs/CHANNEL-CONTENT-SPEC.md, owner 2026-09-19). Inside an organization `media.organization_id` is stamped from `session('current_organization_id')` on upload — an organization member with no organization selected holds no permissions there and cannot upload at all, and the controller would refuse it anyway (422 with a message, never a silent global file). Above the organizations the Media page reads ONE library at a time through its Library list — the platform's own (`organization_id` NULL, `Media::platformOwned()`, files under `media/platform/`; the default) or an organization's (`/media/data?library=platform|{organization}`) — and an upload joins the library chosen (`organization_id` posted, or none for the platform's). NULL, never 0: the column's foreign key cascades, which is what makes a deleted organization take its files. `Media::visibleTo` scopes on the ORGANIZATION ALONE, never on who uploaded: a media file is shared inventory that every colleague in the organization must be able to put on a screen — and a plain `where('organization_id', …)` never matches the platform's NULL rows, so an organization never lists, changes or plays one (a platform file reaches a television only inside a channel). Platform users span every library. Two consequences to preserve: the uploader leaving the organization or deleting their account never touches the file — the menu must not vanish from the organization's screens, so `created_by` goes NULL via the FK and the file stays; and files live on the `public` disk under `media/{organization_id}/` (the platform's under `media/platform/`), with `MediaController::destroy` removing the row and both files (original + thumbnail) together — unless a channel shows the file: then the delete is refused naming the channels (`Media::stillInAChannelMessage`, "Still used by the channel … Take it out of that channel first."), the listing carries the same words (`in_channels_message`) so the page says it before any confirmation, and the same refusal stops an Ad Builder design whose published page a channel shows, before its password is asked. A playlist line is no reason to refuse: the file simply leaves those screens. **Ad Builder ads follow the industry's draft/publish model** (owner, 2026-09-21 — Xibo, Contentful, Strapi; docs/AD-BUILDER-SPEC.md §9): a save changes the draft only, and the screens keep the published page until **Publish changes** (`BuilderAd::hasUnpublishedChanges`, against the version Publish keeps in `published_document`/`published_name`); **Discard changes** goes back to that version; **Unpublish** clears `published_at`, and from then on the page is in no library or picker (`Media::scopeWithoutDrafts` — add it to any new list of media) and on no television, as a line, a channel's ad or a holding picture (`Media::isPlayableNow`, `ChannelAd::statusOn` 'draft') — while every line and channel ad holding it keeps its place, marked as a draft, and plays it again from the next Publish. **And Publish alone decides where an ad may be chosen** (owner, 2026-10-01: "agar publish honga toh hi content library aur channel mein show honga warna nahi honga, aur channel mein add ha toh content library mein show naah ho usko — yeh tick wala kaam hat jayega"): a published ad is offered to a screen's Content library, its holding picture and a channel's pickers alike, a draft to none, and rule (6) of **Channels** keeps one a channel shows off the playlist's picker and one a playlist holds off the channel's, as for every file. The "Show in playlists" tick of 2026-09-22 (`builder_ads.in_playlists`, with `Media::scopeWithoutChannelOnly`, `assertAdsMayBeOnAPlaylist`, `assertMayPlayByItself` and its endpoint) is gone, column and all (2026-10-01) — never bring a second switch back for what rule (6) already decides. **And an ad says how long it is on screen** (`document.duration`, owner 2026-09-28: "8 seconds ki ad aur background 20 seconds toh 8 seconds k bad change honi chahiye" — the industry's way, Xibo's layout duration and Canva's page duration): the design owns its length (`BuilderAd::DEFAULT_SECONDS` = 6 when it says none and `MIN_SECONDS` = 6, a picture's own — owner 2026-09-28 — `MAX_SECONDS` = 300, `BuilderAd::lengthOf()`), set in the editor's Stage panel (`@ad-length`), and Publish writes it onto the page's media row as `duration_seconds` like a video's (`Media::ownLength()`, the published version's — a draft's new length waits for Publish changes, and `builder:recompile` writes the published one). From there every playlist line and channel ad plays the ad that long whatever it was given (`PlaylistController::writeItems`, `DeviceController::lineSeconds`, `ChannelAd::play_seconds`; neither form shows seconds for it, `runs_own_length`/`own_length`), and a video inside it — its background layer's or one on its stage, `autoplay muted loop` — repeats when it is shorter and is cut when the ad ends; each animation the length cuts says so under its timing in the editor (`timingNote`, `anim-in-timing`/`anim-loop-timing`/`anim-out-timing` — an entrance or an exit that starts after the end is never seen, one still running is cut, a loop that starts after it never moves; a loop cut part-way round is not said, it is what a loop is), and the editor's Play and the Preview tab show the ad the same way — for its length, then from the start again (`motion.lengthTimer`; a `refresh` meta in the preview's answer alone, never in a published page, which the player times). **A design has a length of its own only once somebody types one** (`BuilderAd::hasOwnLength` — every new design does, `blankDocument`; one made before 2026-09-28 does not): until then Publish — again, or after Unpublish — writes no length onto its row and every line and channel ad keeps the seconds it was given (the brute-force round, 2026-09-29: a typo fixed and published re-timed a 15 s ad to 6 on every screen); the editor shows the Length empty with a note (`ad-length-earlier`), Play and Preview play on without restarting and the timing notes stay quiet, since there is no one end to go by; emptying the Length gives the length back to the lines; and `builder:recompile` never gives one either, because writing a page again must not change how long the screens show it. An animation time never goes past the longest an ad may be (`AdAnimations::NUMBERS`: an entrance's or a loop's wait and an exit's start at most `BuilderAd::MAX_SECONDS`; `normaliseDocument` brings an older design's later times in when it is opened, so it is saved inside them rather than refused), and the Preview, which reloads at the length for as long as its tab is open, answers 304 while the draft is unchanged (an ETag of the draft) instead of compiling the ad again. A new place that times an item uses `Media::ownLength()` before the line's seconds. **And an ad says which way its screen is mounted** (`builder_ads.orientation`, owner 2026-09-23 — docs/AD-BUILDER-SPEC.md §12): landscape 1920×1080 or portrait 1080×1920, chosen in the New-ad chooser before the editor opens and NEVER changed after — `BuilderAdRequest` measures every save against the saved ad's column (`orientation()`), refusing a stage of the other size, and reads the posted `orientation` on a create alone. The size lives on the model (`BuilderAd::STAGE_SIZES`, `stageWidth()`/`stageHeight()`, `blankDocument($orientation)`) and reaches the compiled page, the media row (`width`/`height`/`orientation`, so pickers say "portrait" for a page as they do for a photograph) and the poster; the page scales its own stage to whatever plays it, bars in the stage's colour, so a portrait ad on a landscape screen is the organization's mistake, SAID on the playlist page (`orientationNote`) and never refused. **Groups are real elements** (`type: 'group'`, spec §13, owner 2026-09-23): what is inside says so with `parentId`, every element keeps STAGE coordinates whatever it is inside, a group's box is the box around its children (`syncGroupBounds` in the editor on every commit, `AdCompiler::groupBox` on the page — never the stored numbers) and a group's rotation is always 0 (turning it turns the children). The rules check the list as a tree BEFORE the per-element rules (`BuilderAdRequest::tree()`, `bail`: a parent must be a group of the design, no circles, at most `MAX_GROUP_DEPTH` = 3 group ancestors), the compiler writes only what a walk from the top reaches, and the editor selects one level at a time (`resolveTarget`, `editingGroupId`). A new place elements are listed, moved, copied or deleted must take a group's whole subtree (`descendantsOf`), and a new per-element check of `locked`/`visible` must climb the ancestors (`isLocked`/`isShown`). Thumbnails use GD (no image package); a video's poster frame and dimensions are measured in the BROWSER at upload time and re-validated server-side, because there is no ffmpeg — and its LENGTH is read by the server from the file itself (`App\Services\VideoDuration`, see **Upload limits**), the browser's number being display only. Accepted formats (JPG, JPEG, PNG, GIF, WEBP, MP4, WEBM) live in `StoreMediaRequest::ALLOWED_MIMES` as the source of truth, and everything that mirrors it must change together: `ALLOWED_EXTENSIONS` in `resources/js/core/media-file.js` (which the shared uploader, `upload-dropzone.js`, imports), the `accept` list in `components/upload-dropzone.blade.php` (one for every page) plus the `hint` each page gives its box (`media/index.blade.php`, `campaigns/index.blade.php`, `channels/show.blade.php`, `builder/assets.blade.php`, the editor's picker in `builder/editor.blade.php`), and the formats in words, `StoreMediaRequest::FORMATS_IN_WORDS`, which the refusal message of every upload request reads (`CampaignRequest`, `ChannelAdRequest` and the Ad Builder's `BuilderAssetRequest`, which also takes `ALLOWED_MIMES` itself). A still format also needs a reader in `MediaStorage::readImage`, or it uploads with no thumbnail.

**Upload limits (owner's rules, 2026-09-28 — "5 min se zyada wali video upload na ho", "Ads Network mein 60 seconds", "Har store ko 512 MB ki storage milegi, koi bhi store 512 MB se upar na ja sake"):** (1) **A video's length is the file's own.** `App\Services\VideoDuration` reads it from the bytes — an MP4's `mvhd`, each track's edit list or media, `mehd` and a fragmented file's fragments (index first or last, 32- or 64-bit boxes); a WebM's `Duration` and its last block (so a browser recording with no Duration is measured too) — and takes the LONGEST of what the file says, so a short header cannot hide an hour; anything malformed, truncated, negative or unrecognised is null, and every loop is bounded — but bytes after an MP4's last box that are no box at all (a phone maker's trailer, Samsung's SEF) end the walk once the movie has been read, as a player's walk ends there (the brute-force round, 2026-09-29: such files played and were refused), while a real box header running past the end is a file cut short and stays refused. A video under half a second rounds to nothing and is refused at every door ("A video must be at least 1 second long.", `VideoLength` and `videoLengthError` alike): kept with no length it was timed as an unmeasured video of two minutes, and a break counted it as nought. `App\Rules\VideoLength` refuses a video over its ceiling and a video nobody can measure ("We could not read how long this video is…"), rounded to the nearest second as a phone shows it; `MediaStorage::put` stores the measured length, never the client's `duration_seconds`. Ceilings: **5 minutes** (`Media::MAX_VIDEO_SECONDS`, mirrored by `MAX_VIDEO_SECONDS` in `resources/js/core/media-file.js`) on the Media page and a channel's Upload (add and change of file); **30 seconds** (`BuilderAsset::MAX_VIDEO_SECONDS`, which the shelf's uploader reads straight from the model — no copy in the browser) on the Ad Builder's shelf — a design's video, a background layer's or one on the stage alike, repeats for as long as the ad is on screen (`loop` in `AdCompiler`), so it only ever needs a short one; **60 seconds** (`Campaign::MAX_AD_SECONDS` = one break) for an advert, a picture's seconds too. Every upload request lists the rule after `bail`, a new upload door adds it, and a video playlist line keeps its FILE's length whatever a save sends (`PlaylistController::writeItems`), because the player's backstop is that length. (2) **Every organization has 512 MB** (`App\Services\OrganizationStorage::LIMIT_BYTES`): what its rows name on disk — its library (uploads, channel uploads into it, the Ad Builder's published pages) and the Ad Builder's shelf at their recorded `size`, plus every preview a row names (a thumbnail, a video's poster, a design's poster and its published copy) at its size on disk, each file once — so a thousand tiny uploads with large posters cannot fill the server under an empty meter. The platform's own library, the Ad Builder's shared shelf and the ads network's files have no wall; a platform user uploading into an organization's library counts to the organization. Every write that adds to an organization is decided in `OrganizationStorage::withRoom` under the organization's row lock, reading what is used INSIDE the lock (the lock is the transaction's first read, as in `OrganizationTeam::changeTeam`), so two uploads at the same moment cannot both fit into the last megabytes; a write that frees room or keeps it the same is never refused, and a refused upload's files are taken away again (`MediaStorage::keptWithinTheWall`). The doors: `MediaStorage::addToLibrary` (the Media page and a channel's Upload) and `addBuilderAsset` (the shelf and `builder:examples`) refuse with "Not enough storage: this needs …, and {organization} has … left of its 512 MB. Delete files you no longer use to make room."; `AdPublisher::publish` refuses a page that does not fit (under `publish`) and the screens keep what they had; a design's poster and a duplicate's copy of it are niceties — with no room they are simply not written (`storePosterWithin`, `withRoomOrSkip`), never a refusal; `builder:recompile` and Discard changes, which rewrite what is there, are not asked. The Media page, the shelf and a channel's Add ad read the organization's `storage` ({used, limit}, null for no wall) from their own JSON (`/media/data`, `/builder/assets/data`, `/channels/{channel}/ads` and every upload and delete answer) — the meter is `<x-storage-meter>`, and the upload forms refuse a file bigger than what is left before a byte is sent (`storageError` in `media-file.js`); the server decides. A new place an organization's bytes are written goes through `withRoom`, and a new preview is named by a row so it is counted. (3) **The server's own disk keeps its reserve** (owner's decision, 2026-09-29 — anybody with an inbox can make an organization, and the platform's library and the ads network have no wall of their own): `App\Services\DiskGuard::assertRoomFor` refuses an upload at every door — the Media page and a channel's Upload (`addToLibrary`), the shelf (`addBuilderAsset`), a campaign's file (`storeCampaignFile`) and a publish (`AdPublisher`, under `publish`), whoever uploads — once the disk would keep less than `signage.upload_reserve_bytes` (`SIGNAGE_UPLOAD_RESERVE_MB`, 5 GB by default, none under the test suites unless set): "The server is almost out of space, so uploads are paused for now. Please try again later: the team has been told." Every super admin gets `DiskAlmostFullNotification`, at most once in `DiskGuard::ALERT_HOURS` (6, a `Cache::add`), a mail server's refusal is reported and never thrown, and a system that cannot say what is free refuses nothing. A new upload door calls it before a byte is written. **Long before that the super admins are warned** (owner's rule, 2026-09-29: "server per jab 10gb khaali rahe toh email aye"): `php artisan disk:check`, scheduled every hour, emails `DiskSpaceLowNotification` while less than `signage.disk_warning_bytes` is free (`SIGNAGE_DISK_WARNING_MB`, 10 GB by default, none under the test suites unless set) — uploads still working — at most once in `DiskGuard::WARNING_HOURS` (24), and at once again after the disk has been above it in between. It looks on the clock, not at uploads, because a disk fills without an upload too: MySQL's binary logs (30 days by default, a line a minute per television from its heartbeat), the nightly backups, the logs.

**Uploads — dropped, sent in chunks, shown as they go (owner, 2026-09-29 — "drag and drop lagana ha chunking karni ha aur acha se progress bar dikhana ha"; docs/UPLOADS-SPEC.md):** every page that takes a file uses ONE uploader, `<x-upload-dropzone>` (`components/upload-dropzone.blade.php` + `resources/js/core/upload-dropzone.js`, Alpine `uploadDropzone`): a box a file is dropped on or chosen with, and a row per file with its preview, a bar, the speed and the time left, and Pause/Resume, Cancel and Try again — in the panel's own look. The bytes travel by tus 1.0 (creation + termination) through Uppy's ENGINE only (`@uppy/core`, `@uppy/tus`, MIT, loaded when a file is chosen — never Uppy's Dashboard), 5 MB a request, to the app's own endpoints (`UploadController`, `App\Services\ChunkedUploads`, the `SpeaksTus` middleware — no server package): `POST /uploads` opens an upload only after asking everything the finished file would be refused for (the permission and the place per purpose, the format by its name, the size, the organization's 512 MB counting every upload still open for it — under the organization's lock — and the server's reserve counting every open upload's missing bytes); `PATCH` writes a chunk at its offset under the row's lock (409 at another offset, 413 past the end); `HEAD` says how far it got; `DELETE` gives it up; somebody else's upload is 404. The routes sit behind `auth`, `verified`, the named limiter `uploads` and CSRF. With every byte in, the page posts the door it always posted with `upload` (the id) in place of `file`: the four doors' Form Requests (`StoreMediaRequest`, `ChannelAdRequest`, `CampaignRequest`, `BuilderAssetRequest`) make it the request's `file` in `prepareForValidation` (`Concerns\TakesAFinishedUpload`: the person's own, finished, unexpired, opened for that door, one request at a time under a cache lock), so every rule — the format read from the bytes, a video's length from the file, the organization's wall, the reserve — runs exactly as for a file posted whole, and the controller forgets the upload once its row is made (`forgetFinishedUpload`). **A new upload door does all three:** its request takes the trait, its controller forgets, its page uses `<x-upload-dropzone>`. Two modes: `add` (the Media page and the shelf, the box on the page itself, and the Ad Builder editor's picker — several files, each posted as it arrives, titled by its name; its "Added" row fades away after eight seconds, as a notification does — `ADDED_STAYS_MS`, owner 2026-09-30 — while "3 of 5 added" still counts it until nothing is going any more, and a refused or failed row stays for its reason) and `form` (a channel's Upload, a campaign's advert — one file; Save waits for it, `upload-busy`). A page listens for the box's events on an element of its OWN around it (the Alpine gotcha below). The parts are `{id}.part` on the `uploads` disk, a root per environment as `public` has (`storage/app/private/uploads`, `dusk-uploads`, `framework/testing/uploads`), because `uploads:prune` — hourly: an upload expired after 24 hours, and a part no row names after an hour — must never see another database's parts; `DuskTestCase` sweeps a test's own. A connection that fails is tried again for some 25 minutes (`RETRY_DELAYS`), an offline browser waits and carries on the moment it is back, a request silent for 30 seconds is sent again, the bar never goes back, and a page left mid-upload asks first. The browser still checks what it can before a byte (`fileError`, `storageError`, `videoLengthError`); the server decides.

**Screens & the device API (the one machine-facing surface):** a TV has no session, so `routes/device.php` is registered OUTSIDE the `web` group — no cookies, no CSRF, four endpoints only (`register`, `pair-status`, `playlist`, `heartbeat`). Deliberately NOT `routes/api.php`: the owner's no-API rule stands, this is a narrow device channel with its own stateless stack. Rules that must hold together: **open ≠ unauthenticated** — `register` is open but throttled 30/min per IP, `pair-status` is open but demands the `poll_secret` issued at registration (so a guessed uuid cannot steal a freshly minted token), and everything returning real content sits behind `device.token`. A screen's identity is a 64-char random token **stored only as a SHA-256 hash** and handed to the device exactly once, on its first successful poll, after which the `pairing_requests` row is destroyed. Pairing codes are 6 characters from an alphabet with no `I/O/0/1` (read off a TV across a room), live 15 minutes, and are created only when a player actually opens — so there is nothing to clean up but strays. `screens.organization_id` follows the media wall: stamped from `session('current_organization_id')` at pairing, `Screen::visibleTo` scopes on the organization alone, and a screen from another organization 404s. Re-pairing an existing screen rotates its token in place (old device locked out on its next request, playlist and settings kept) instead of creating a second row. **`DevicePairing::claim()` looks the row up INSIDE its transaction with `lockForUpdate()`** — a code answers to exactly one screen, and reading it unlocked let two people (two staff, two tabs, a retried request) both be told "screen added" while only one token can be stored, leaving the loser with a screen whose token nobody holds: permanently offline, and silent about why. Deleting a screen is how you revoke a device: it gets 401 and falls back to showing a fresh code. **Every throttle on this app uses a NAMED limiter (`AppServiceProvider::registerRateLimiters`), never the bare `throttle:n,1` form.** That form keys on domain+IP alone for a request with no logged-in user — the route is NOT part of the key — so every route using it shares one counter per visitor. An organization's TVs and the owner's laptop share one public IP, and each paired screen sends three requests a minute, so the bare form let a handful of screens exhaust the signup form's budget and lock a new TV out of pairing while the running screens hid the problem. The device limiters therefore count PER DEVICE (`device-api` by token hash, `device-pair` by `device_uuid`, each with a looser per-IP ceiling); only `device-register` keys on IP, because a screen asking for its first code has nothing else to be known by. `throttle:device-api` also runs BEFORE `device.token`, so a wrong token is rate limited too. **The player is a progressive web app that keeps playing offline** (docs/AD-BUILDER-SPEC.md §15, owner 2026-09-23): `public/player-sw.js` — plain ES5 at a fixed address, never built by Vite, registered at scope `/player` so the panel is never served from a cache — keeps four caches. The **shell**: the page (network first) and the built files it names, kept together or not at all, so a set rebooting with no line never has a page whose scripts are missing (the page's inline watchdog reloads one whose script never ran). The **manifest**: the last `/device/playlist` answer PER SCREEN (keyed by a digest of the token, never the token), network first with an 8 s patience — a 401 goes through untouched; only an unreachable server, a 5xx or an answer that is not JSON (a captive portal) falls back to it, marked `X-Signage-Cached`; a late answer is kept anyway. The **media**: every file by VERSIONED address, matched exactly (`assetUrl()` appends `?c=checksum`, the runtime carries `?v=`; with no line and no copy of that version, the same file's previous one plays instead). The **parts**: a big file fetched 4 MB at a time by range requests, so a download cut short carries on. ONE warm-up, however often the player asks: one file at a time, most needed first, files and the runtime only and never with cookies, then the prune, which keeps an older version until the named one is in. The manifest carries `fallback` (the holding picture) and a **`timeline`** — what the screen shows at every moment its answer changes over the next 72 hours (a rule's hours and days, a line's dates, campaign windows), worked out by the same resolvers that answer online — which is also every file the player warms: nothing further off reaches the device. An Ad Builder page plays in a frame opened at `/player/page?src=…`, inside the worker's scope (so what it loads comes from the cache on every browser with a worker — a `srcdoc` frame is a worker's client only from Chrome 135), `sandbox="allow-scripts allow-same-origin"` — a frame with an origin of its own is served by no worker — and the page carries its own Content-Security-Policy (`AdCompiler::contentSecurityPolicy`: inline scripts by digest, the runtime's folder, no request, form, frame, plugin or base of its own); with no worker the page plays straight from the server with `allow-scripts` alone. `php artisan builder:recompile` writes every published page again from the version on the screens (never the draft), and every deploy runs it with `--outdated` after the site has switched over (`deploy/server/release.sh`): each page's head names the compiler that wrote it (`AdCompiler::VERSION`), and only pages an older compiler wrote are written again — so **move `AdCompiler::VERSION` whenever what the compiler writes changes in a way the published pages should get too**, or they keep the old output. Offline, the player plays the timeline's entry for now (past its end, the last one) by its own clock corrected by the last live `server_time` (kept across reboots, never earlier than the manifest) — the server already put the holding picture in every entry with nothing else due, or left it black; the loop restarts only when what would be shown changes. Heartbeat, register and pair-status are never cached: a heartbeat that cannot get out is what tells the panel a screen is offline, and nothing on the television says so (owner's rule). A new file kind a screen plays must reach the timeline's `lines` and use `assetUrl()`; a new device endpoint must decide whether the worker may cache it. **And it runs on old WebViews** (owner, 2026-09-24): a Fire TV, a cheap Android box and the Android player app (`com.digitallifts.player`, its own project outside this repo) may carry a WebView as old as Chrome 80, so the player page loads no stylesheet but its own (Tailwind v4 needs Chrome 111; the few reset rules it relied on, `[hidden]` among them, are written in its `<style>`), uses no CSS that floor lacks (`inset` is Chrome 87), Vite writes the syntax down to `chrome80` (`build.target` in `vite.config.js`; the stylesheets keep Vite's default, so the panel's CSS is unchanged) and nothing a television runs — the player's script, its worker, the ad runtime — calls a newer API. `PlayerOnOldWebViewsTest` holds all four, and the Android app blames the WebView only below the same floor.

**Playlists (the thing a screen actually plays):** `playlist_items` is an ordered list of lines — each one a file `(media_id, duration_seconds)` or a channel `(channel_id)`, exactly one of the two (see **Channels**) — written by **replacing the whole list in one PUT** rather than patching positions — reorder, retime, add and remove are then the same call, it is atomic, and a half-finished rearrangement never reaches a TV. Three rules that must hold together: a screen may only play **its own organization's** files (`PlaylistController::assertMediaBelongsToTheSameOrganization`, 422 otherwise — the organization wall in the one place it is easy to forget); the **schedule is resolved server-side** in `DeviceController::playlist`, so a line its rules keep off the air never reaches the device and a cheap box with a wrong clock still shows the right thing — a file keeps its name alone, with no dates or description of its own (owner, 2026-10-01: "srif naam rakho"; the Media page's Rename), and when it plays is its line's rules alone; and every manifest item carries a **`checksum`** — a cache key that moves only when the bytes may have, not a content digest: a picture's or a video's is the file itself (id, size, path — every upload is a new file with a name of its own, so a new title sends no television to download it again); an ad page, rewritten in place on every publish, adds its row's stamp; a channel ad's is its file's own (one file on a playlist and in a channel is one copy on the set), a campaign's is its file (`Media::cacheKey()`, `ChannelAd::cacheKey()`, `Campaign::cacheKey()`) — so the player's worker, or a future native shell, can decide whether the copy it already has is current. Reading a playlist is `screen-view`; WRITING one is `screen-playlist`, which also gates the picker's own media endpoint so it never drags in `media-view` (see **Capability-complete permissions**). Deleting a file cascades it off every screen it was playing on. **A save carries a `version`** — `Screen::playlistFingerprint()`, a content hash handed out by the GET and required by the PUT — and a mismatch is a **409**, never a silent overwrite. A file or a channel deleted while a save is on its way is found under the same lock and refused with a reason (422), never left to the foreign key's 500. Because the PUT replaces the WHOLE list, a client working from a stale copy would otherwise erase whatever a colleague changed in between with nothing to show for it; the fingerprint is content-based so re-saving an identical list is not a conflict, and the PUT returns the NEW version so one page can save twice. Nothing polls for it — it travels with the save that was already happening, so this needs no websockets.

**Schedules — the time is on the rule (owner, 2026-10-01 — "dayparts ko hata k kahi Playlist mein jab schedule set karte ha waha nahi dal sakte?", then "theek ha kardo"; docs/SCHEDULE-SPEC.md §21):** a line's schedule rule says WHICH DAYS (every day, between dates, or a repeat) and WHAT TIME — the whole day, or from one clock time to another, typed in the schedule window itself: `schedule_rules.start_time`/`end_time`, both or neither (`PlaylistController::ruleRules`, "Time: give both a start and an end, or choose All day."), never equal, an end before the start running past midnight and belonging to the day it OPENED on (`ScheduleRule::coversAt`, `openWindowDay`: half past midnight on Saturday is Friday's night). **There are no dayparts** — no page, no table, no `daypart-*` permission, and the word is gone from the panel: whoever may change a playlist (`screen-playlist`) sets its hours, as 21 of the 23 signage products looked at do (the time typed where the schedule is set; only Xibo keeps a library of named dayparts). Other hours on one weekday are a second rule on the line — a line plays when ANY of its rules says yes — and a closed weekday is simply one no rule names. What the named daypart gave, one change reaching many lines, is **Copy to Other Lines** in the schedule window (`copyToKeys`, `applySchedule`: staged on the page like every edit until Save Changes) and Copy to Other Screens beyond it. **Weekdays** and **Weekends** tick the usual sets of a weekly repeat at once (`setWeekdays`), and a line whose every rule is over by the SCREEN's own calendar says **Ended** (`scheduleEnded`, read against `local_date` in the playlist's answers — never the browser's date; hours past midnight end a day later). The migration that moved every daypart's hours onto the rules that named it is held to "exactly what it said before" by `ScheduleTimesMigrationTest`, half hour by half hour for two months — a daypart with other hours on some weekdays becomes a rule for each set of hours — and it stops before changing anything for a rule it cannot carry over, naming it. A new place that times a line reads `ScheduleRule::hasTimes()`/`clockTimes()`, and a second, named list of hours is never brought back for what a rule already says.

**Channels (content an organization may carry):** a channel (`channels` + `channel_ads`) is one of two kinds (owner's rules, 2026-09-16). The **platform's** channel (`organization_id` NULL) is made ABOVE the organizations — by the super admin, or a global role holding `channel-view/store/update/destroy` — and is offered to EVERY organization, with no organization targeting and no per-ad targeting. An **organization's own** channel (`organization_id` set) is made inside an organization by a member whose role there carries the channel permissions, and is offered to that organization's screens alone. A channel keeps no files of its own (docs/CHANNEL-CONTENT-SPEC.md, owner 2026-09-19): each ad holds a row of a media library by `channel_ads.media_id` (required, never a copy — publish an Ad Builder ad again and the channel shows the new page), named in the Add-ad form from the **Library**, the **Ad Builder**'s published ads (the same library's `html` rows) or a fresh **Upload** that joins the channel's library first — the organization's for an organization's channel, the platform's for the platform's. An organization's channel takes that organization's rows only; the platform's channel its own library or any organization's (`ChannelAdRequest::chosenMedia`, 422 otherwise); the pickers read `/channels/{channel}/library` under `channel-update`, never `media-view`, and taking an ad out leaves its file in the library. (Ads made before the change were carried into the libraries by a migration that named each file where it lay, so the old `channels/{id}/` shelf still holds theirs.) Six rules that hold together: (1) **reach** — every CHANGE goes through `Channel::visibleTo` (above the organizations: every channel, each listed with whose screens it reaches; inside an organization: that organization's own — the platform's and another organization's are 404, `ChannelAdController`'s controller middleware included, before an upload is even validated), and every LOOK through `Channel::listableIn`, which inside an organization adds the platform's channels, listed and opened read-only (owner 2026-09-19: marked "From the platform", `read_only` on the row and `$readOnly` on the page, no Edit, Delete or Add ad, the screen counts of that organization alone and no name of whoever on the platform made it) — another organization's stays 404; a channel made inside an organization is stamped with it, and a name need only stand apart within what one organization's box lists — the platform's channels and that organization's own (`ChannelRequest`; an organization's name never blocks the platform's); (2) **the organization wall on playlists** — a screen's Channels box and its saved lines take the platform's channels and the screen's own organization's only (`Channel::availableTo`, `PlaylistController::assertChannelsAreAvailable`, 422 otherwise), and deleting an organization deletes its own channels, their ads and the lines carrying them (`Organization::purgeChannels`) — the files are the organization's library, which `purgeMedia` takes, and with it, through `channel_ads.media_id`'s cascade, any ad of the platform's channel that showed one of them; (3) **the organization chooses** — a channel reaches a screen only as ONE playlist line (`channel_id` set, `media_id` and `duration_seconds` NULL) that an organization user adds with the Add button in the Channels box, below Content library; the line plays at its position, carries its own schedule rules like a file, is copied with the playlist, and `Screen::playlistFingerprint` prefixes it so channel 7 never reads as file 7; (4) **resolved on the server** — `ScheduleResolver` sends a channel line only while the channel is active and has ads inside their dates on the SCREEN's local date; **Blade gotcha — `@json` in an `x-data` attribute (caused a real bug):** `@json` encodes with NO flags, so its quotes stay raw and the first string in the payload closes the surrounding `x-data="…"` attribute — Alpine then receives half an expression and the whole component silently fails to initialise (`items is not defined`, an empty table, no error page). Booleans and ints are safe, which is why every earlier page got away with it. Anything carrying a string or an array must use **`{{ Js::from([...]) }}`** instead, which hex-escapes for exactly this position; pass the whole config object through one `Js::from` rather than mixing the two.

**Blade gotcha (caused a real bug):** `@error`/`@if` directives do NOT compile inside a Blade COMPONENT tag's attributes (`<x-text-input class="... @error(...) ... @enderror">` puts the literal text into the class list). Inside component attributes use echo syntax instead: `{{ $errors->has('field') ? '!border-red-500' : '' }}`. Directives are fine in plain HTML elements and inside component templates/slots.

**Blade gotcha — one `@php` form per file (caused a real bug):** Blade lifts `@php … @endphp` blocks out BEFORE anything else is compiled, matching from the first `@php` it finds — so a file that already uses the inline `@php($x = …)` form and then adds a block reads everything between the two as one PHP block, and every page including it dies with a parse error (the sidebar once took down every page). Keep to one form in a file, and never write those words inside a Blade comment either — comments are stripped after the blocks are lifted.

In the CSS: `.form-select` is a component rule, full width, so a select is narrower only from `sm:` up (`form-select sm:w-44`); a class that repeats what a utility or component beside it already applies (`block w-full` on a `form-input`, `whitespace-nowrap` on a `badge-*` or `btn-*`, `text-sm` on a field inside the 1024 px editor) is not written; and a new shared look becomes a `@utility` in `app.css` once, not a class string copied onto every page. **CSS gotcha — a colour only in an Alpine binding (caused a real bug):** before Alpine starts, an element with a border width and no border colour of its own is drawn in the text's colour (Tailwind v4's default), so the Assets page's drop box flashed a black dashed border on every visit, and the Members tabs a black underline. A state's colours are written on the element, and the state picks them: `data-[dragging=true]:`, `aria-pressed:`/`aria-selected:`, `has-checked:` — or a shared utility that reads the state itself: `tab-link` for every row of tabs (the open one by `aria-current`, `aria-selected` or `aria-pressed`, a tab list's first `aria-selected` written into the page) and `role-choice` for a choice boxed round its radio. **A picked tile in a scrolling picker** says so with its own `border-2` and a tick, never a `ring` — a shadow drawn outside the tile, which the scrolling box cut at its edges and which read as a stray shadow — and a keyboard's ring there is `ring-inset`. **CSS gotcha — words for a screen reader inside a table (caused a real bug):** `sr-only` is absolutely placed, so one in a table's cell, whose nearest positioned ancestor is outside the card's `overflow-x-auto` wrapper, is not clipped by it and widens the PAGE from where the cell sits — the Members page scrolled 534 px sideways on a phone for a hidden "Nothing to change" in its last column (`EveryPageFitsAPhoneTest` caught it). Its parent gets `relative`.

**Validation gotcha — a validated array's ORDER is not the client's order (caused a real bug):** `$request->validate()` rebuilds nested wildcard data RULE BY RULE, not row by row: for `items.*.media_id` it sets every row that HAS a media_id, then for `items.*.channel_id` every row that has one. A row missing the first key is therefore inserted into the result AFTER rows that have it, so `array_values($validated['items'])` reads a different order than the client sent — a playlist saved "channel first, poster second" reached the television the other way round, and only a browser test caught it (backend tests had sent the kinds in the lucky order). The keys are still the client's indexes, so anything that cares about order must `ksort()` first (see `PlaylistController::writeItems`) — never trust the array's own order when rows can have different shapes. For the same reason, ids are validated `min:1`: a posted `0` reads as "no id" to `filled()`/`->filter()` and would sail past the ownership checks into a foreign-key error.

**Alpine gotcha — no getters in `extraState`/`extraMethods` (caused a real bug):** `createCrudTable` merges both with object spread (`...extraMethods`), and spread READS a getter instead of copying the accessor. A `get allOnPageSelected() { return this.items.length … }` therefore runs at merge time, with `this` bound to the plain literal rather than the Alpine component — `this.items` is undefined, it throws, and the whole `xxxTable()` call dies before Alpine ever evaluates the `x-data`. The page then renders with an empty table and EVERY binding on it reporting "not defined", including bindings that have nothing to do with the new code. Write a plain method and call it with `()` from the view; getters are only safe in `crud-table-base.js`'s own object literal (see `endItem`), which is never spread.

**Alpine gotcha — an object with private fields never goes into a component's state (caused a real bug):** Alpine wraps its data in a Proxy, and a class's `#private` fields cannot be read through one — Uppy kept in a component's data answered every file with "This file could not be sent". Keep such an object in a variable of the component's closure (`let uppy = null` in `upload-dropzone.js`), never on `this`.

**Alpine gotcha — a page listens on its own element, never on another component's root (caused a real bug):** an `x-on:` written on a component's root element is evaluated with THAT component's `this`, so a page's `x-on:upload-added="onUploaded(…)"` on the dropzone ran the page's method as the dropzone — the page's list refresh wrote into the dropzone's own `items`, and its rows turned into media rows. Put the listener on an element of the page around the component (the events bubble), and never give a shared component's state a name a page uses (the dropzone's rows are `uploads`, not `items`).

**Big deletes re-confirm the password (owner's rule, 2026-09-16):** deleting an organization (platform or Settings → Organizations), an account (platform or Profile), a role, a permission, a channel, a campaign or an Ad Builder design, removing a member (Members page, or the platform's Users → Organizations), and taking a platform role all ask for the actor's password; everyday deletes (a media file, a screen, a channel ad, an Ad Builder asset, an invitation) stay one confirmation away. Changing your own password re-confirms it too. Server: `Concerns\ConfirmsPassword::confirmPassword($request, $bag, $field)` — one shared counter per person across all of these forms, JSON or plain (a plain form gets the error in its named bag) — called AFTER every other refusal so nobody types a password for something refused anyway, messages "Password is required." / "The password is incorrect.", and five wrong passwords a minute per person then a 429 ("Too many wrong passwords…"). UI: `<x-crud.password-confirm>` inside a real `<form>` (Chrome autofill), `deleteNeedsPassword` on `createCrudTable` or the page's own password state, the password error under its field. A new big delete adds both halves in the same commit.

**Frontend guards:** every AJAX action needs an in-flight flag (`saving`/`deleting`/...) with a disabled binding; plain forms are covered globally by `resources/js/core/form-guard.js`. Every form gets client-side validation via `resources/js/core/validate.js` mirroring the backend rules — the backend stays the source of truth.

**Deleting (owner's rules — nothing cascades through people):**
- **Remove a member / leave an organization:** the membership row only. Their uploads, paired screens, playlists and custom roles stay with the organization; `created_by` on content is history only (the FK goes NULL when an account is deleted) and nothing is ever deleted through it.
- **Delete an account** (Profile, or the platform's `user-destroy`): the account and its memberships — nothing else of anybody's — and nothing is left pointing at it (owner's rule, 2026-09-17): the memberships go through their foreign key, `created_by`/`invited_by`/`actor_id` empty (what the person made stays with its organizations, and the log keeps their name), and the `deleted` hook in `User::booted()` removes their sessions on every device (database driver), their password-reset token and every invitation waiting for their email (`User::invitationsToEmail()` — to an organization or to the platform, expired ones included; the deletion's log line counts them). Invitations the person SENT stay with their organizations (`invited_by` empties). Self-deletion is refused while the person is the last Owner of any organization (the message names the organizations); a platform deletion goes ahead (the response names the organizations left without an Owner) and the super admin gives them one with "Invite owner" on the Organizations page or from Users → Organizations. Super admins cannot delete themselves; deleting a platform account needs a super admin, and deleting a super admin the primary one. NO soft-delete for users, by explicit owner decision. An account never confirmed goes by itself after `User::UNVERIFIED_DAYS` days, with its empty organization (see **Email verification**).
- **Delete an organization** (`organization-destroy`: inside an organization — the Owner's by default — the organization the person works in, from Settings → Organizations; on the platform any organization, from the Organizations page — always typing the name and their password; the name to type stands out in the sentence that asks for it, `confirm-name`, owner 2026-10-01): everything the organization owns goes, through the `deleting` hook in `Organization::booted()` → `Organization::purgeContents()` (BEFORE the row goes: the foreign keys would otherwise take the media rows first and leave their files with no row to name them) — memberships, invitations, custom roles, screens (their playlists and schedule rules with them; a device loses its token), the organization's own channels through `Organization::purgeChannels()` (their ads and the lines carrying them; their files are library rows, next), the whole media library through `Organization::purgeMedia()` (owner's rule, 2026-09-15): every row whoever uploaded it — and, through `channel_ads.media_id`'s cascade, any ad of the platform's channel that showed one of them — the rows inside the transaction and the files only after it commits (`DB::afterCommit`), and only the paths the rows name are unlinked — never a whole folder — and its Ad Builder designs and asset shelf through `Organization::purgeBuilder()`, the same way (rows inside the transaction; each design's poster and each asset's files after commit, by the paths the rows name), and the uploads still on their way into it through `Organization::purgeUploads()` (the rows, then each part by the name its row gives). **The organization row goes too, for good** (owner's rule, 2026-09-17: "A to Z" — there is no soft delete and no `organizations.deleted_at`), and `roles.organization_id` cascades, so a custom role can never outlive its organization and turn into an organization role offered everywhere. The people's accounts stay, and so does the activity log: its entries keep the organization's id, and its name in their words.

**Activity logging:** every mutation endpoint calls `ActivityLog::record()` (action like `member.invited`, subject, human description). When adding a new mutation endpoint, add its log line in the same commit. For actions performed while unauthenticated (e.g. password reset via email link), pass the acting user explicitly as `record()`'s fourth `$actor` argument. Deliberately NOT logged (owner-accepted noise/no-op exclusions): failed login attempts, forgot-password link requests, `confirm-password` (session-only), and asking for a verification link again (the signup's or a changed email's: a mail request, like forgot-password), and the chunks of an upload (`/uploads` — the file is logged when it joins its place, by the door that adds it). **Which organization an entry belongs to:** `activity_logs.organization_id` — `record()` takes it from the subject (an organization, or anything with an `organization_id`: a screen, a media file, a custom role, an organization's channel, an invitation), or from its fifth argument `organizationId:` wherever the subject is gone (a delete) or is a person (a member's role changed or removed). **Upload gotcha — `UploadedFile::fake()` believes the filename (weakens a real test):** a fake file's mime type comes from its NAME (`Illuminate\Http\Testing\File::getMimeType()`), while a real upload's comes from its BYTES (finfo). So `fake()->createWithContent('shell.jpg', '<?php …')` passes `mimes:jpg` in a test and is refused in production — the test proves nothing. To test what the server really does with a lie, build a real one: write the bytes to a temp file and `new UploadedFile($path, 'shell.jpg', 'image/jpeg', null, true)`, where the third argument is only what the CLIENT claims (`uploadWithBytes()` in `FileUploadAttackTest`). Keep `fake()` for size and for formats whose name and bytes agree — never for a VIDEO: the server measures a video from its bytes (**Upload limits**) and a fake has none, so it is refused. `Tests\Support\VideoFiles` builds real MP4 and WebM containers of any length and layout, and `VideoFiles::upload($bytes, $name, $reportedKilobytes)` can report a size larger than the bytes for the storage tests.

**Test gotcha — a session assertion between two requests empties the next page's errors (cost a debugging round, 2026-09-29):** this app keeps its sessions as JSON (`config/session.php`, `serialization`), so the session store turns the error bag into an array when it saves and back into a bag when it starts. `assertSessionHasErrors` (any `TestResponse` session assertion) starts it between two requests of one test, and the next request then marshals the same in-memory bag a second time — into an empty one — so the page after it shows no error although the redirect flashed it. A browser never meets it (every request loads the array afresh). A test that wants the error ON the page asserts the page alone, with no session assertion in between.

**Input gotcha — text that is not UTF-8 (caused real 500s):** a browser never sends it, but a request made by hand can, and such text passes every `string` rule — then broke whatever turned it into JSON (a 500 from the screen update, the screen listing's search and the channel create, "Malformed UTF-8 characters"), a MySQL row or a limiter's key. `RejectMalformedText` is PREPENDED to every route in `bootstrap/app.php` — the device API's too — and answers 400 before anything reads the query, the form, an upload's file name or the User-Agent the session keeps. Keep it first; never move it into a group.

**Input gotcha — a query parameter can be ANY shape (caused a real bug):** `?search[]=x` arrives as an array, and an array reaching a `like` clause, a `trim()` or a cache key is an "Array to string conversion" — which Laravel raises as an error, so the answer is a 500. It cost every listing in the panel and, worse, the device API's own limiter (`device-pair` keys on `?device_uuid`, and a limiter runs BEFORE the endpoint's validation, on a surface that is open on purpose). Wherever a word is read straight out of a request with no Form Request having checked its shape first, read it through `HandlesCrudData::plainValue()` — anything that is not one plain value reads as "not sent", which keeps a listing forgiving — or validate it (`['search' => ['nullable', 'string', 'max:255']]`, as both media pickers do).

**Validation gotcha — a later rule still runs after `string` failed (caused real bugs):** Laravel runs every rule for an attribute unless the list begins with `bail`. A `name` posted as an array therefore failed `string` and then reached the closure that folds the name to compare it — `(string) $value` on an array, a 500 (`RoleController::validated`, `ChannelRequest`); and a `password` posted as an array failed `string` and then reached `current_password`, which hashes whatever it is handed — a 500 on EVERY big delete in the app (`Concerns\ConfirmsPassword`). All three now begin with `bail`. Any rule after a type rule that assumes the type held — a closure, `current_password`, `exists`, a custom Rule object — needs `bail` in front of it; a closure that only compares with `!==` (the organization-delete confirmations) is shape-proof and does not. The same applies one level down: a list validated as an `array` says nothing about what is INSIDE it, so a mapper typed `array $row` over `rules` blows up on `rules[]=x` until the elements are validated too (`PlaylistController::preview` now reuses the PUT's own `ruleRules()` for that).
