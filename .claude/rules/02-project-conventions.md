# Project Conventions

Enforce on EVERY change — and when fixing a gap, sweep the whole class of it project-wide, not just the reported instance.

**Authorization model (three tiers):**
- **Super-Admin** = the role named `Super-Admin`, held on the `store_user` sentinel row `store_id = 0`. Only super admins may: assign global roles, remove global (store-0) assignments, create/edit global roles, impersonate.
- **Global users** = anyone holding a role with `is_global = true` on the store-0 sentinel (`User::globalRole()`). They span every store: see all stores, assign/remove users in any store, get the global stats dashboard. Their powers are still limited to their role's permissions.
- **Store users** = assigned to real stores via `store_user` (one role per store). They act only within stores they are assigned to, in the session's `current_store_id` context.

**How users enter the system (two doors, both create owner + store together):**
- **Public self-registration** (`/register`, routes/auth.php): a customer signs up with their store in one form. The assigned role is ALWAYS the single role flagged `is_signup_default` — server-chosen, never client input. Only a super admin may set that flag (roles UI checkbox); exactly one role holds it at a time; a global role can never hold it. New owners are attributed to `User::firstSuperAdminId()`; their store's `created_by` is the owner.
- **Admin onboarding** (`POST /users/onboard`): the same one-step flow performed from inside, requires `user-store` + `store-store` + `user-store-assign` together; the role comes from the request but is validated against `visibleTo` and must not be global.
- **No API:** this is a web-only app — there is no `routes/api.php` and no token API, by owner decision (a half-built mobile login was deleted 2026-09-03). Do not add API routes without explicit instruction; any future API needs validation, throttling, and tests from day one.

**Ownership & visibility:** users and roles are visible one level deep via `created_by` (super admins see everything except unrelated super admins), and for a store user that is narrowed further by the store they are working in — see **Per-store isolation** below. Every WRITE endpoint that targets a user/role/store must scope its target: `visibleTo()->findOrFail()` for users/roles, `ensureStoreAccessible()` for stores. Route middleware (`can:`) alone is NOT enough.

**Tiers are mutually exclusive:** a user is EITHER global (store-0 sentinel) OR store-assigned — never both. `assignStore` rejects a store assignment for a global user and a global role for a store-assigned user (remove the other tier first). The assign modal hides the store form for global users.

**Role visibility matrix:** super admin → all roles; global users → all NON-global roles from any creator (they assign across stores) but may MODIFY only roles they created (403 otherwise — seeing ≠ editing); store users → only roles they created **in the store they are currently working in**. Global roles (Super-Admin included) are visible, assignable, and editable by super admins only. Any change touching visibility/permissions must be checked against all three tiers before it ships.

**Per-store isolation (the store is the wall):** permissions are evaluated against the CURRENT store's role, so every action must land in that same store, and **whatever a store user creates belongs to the store they created it in**. Four enforcement points, all required together:
- **Stores & assignments:** a store user may only act inside `session('current_store_id')` — `ensureStoreAccessible()` for stores, and assign/unassign refuse a different store (403). Holding a permission in store A grants nothing in store B; in store B you get exactly what store B's role gives you.
- **Users are the ONE thing that is NOT store-scoped — deliberate (owner's decision):** `User::visibleTo` stays `created_by = actor`, with no store condition, so the people you created follow you into every store you work in. *Reason: otherwise a store owner working in two stores could not staff their second store themselves — they would have to ask a super admin to move each person across, which is friction for no security gain (they already control both stores). The wall that matters is the ROLE: in the other store they can only hand out that store's roles, so the powers granted there are exactly what that store allows.* Never add a store filter to user visibility without the owner's say-so.
- **Roles:** `roles.store_id` records the store a role was built in (NULL = store-less: global roles, and roles made by super/global admins who have no store context — those stay usable anywhere). `Role::visibleTo` requires `created_by = actor AND store_id = current store`, so a role made in store A is invisible — and therefore unassignable, uneditable, undeletable — from store B. `assignStore` additionally rejects a store-scoped role whose `store_id` does not match the target store (422). Anything that creates a NEW store alongside its owner (public signup, admin onboarding) demands a store-less role — a role tied to an existing store can never govern a new one.
- **Permission checklist:** `User::assignablePermissions()` resolves against the current store's role, so a role built in store B can never carry permissions the actor only holds in store A.
With no store selected, a store user sees nothing at all (empty scope, not an unfiltered list). When adding any new store-scoped entity, stamp it with the store on create and add the same walls in the same commit.

**Capability-complete permissions:** a permission must be self-sufficient for its task. Option lists that feed an action (e.g. the assign modal's store/role dropdowns) come from dedicated endpoints gated by the ACTION's own permission (`/users/assignable-stores`, `/users/assignable-roles` → `can:user-store-assign`), returning only the minimal fields (id + name). Never make a feature depend on unrelated `-view` permissions of other modules.

**UI permission gating:** every action element (Add/Edit/Delete/Assign/Remove buttons, nav links) must be wrapped in `@can('<permission>')` matching its route's `can:` middleware. The UI hides; the backend enforces. When adding any button, add its gate in the same commit.

**Role permission subsets:** a role's permissions must be validated server-side against the creator's `assignablePermissions()` (see `RoleController::assertPermissionsAreAssignable`). The UI checklist filter is cosmetic.

**Blade gotcha (caused a real bug):** `@error`/`@if` directives do NOT compile inside a Blade COMPONENT tag's attributes (`<x-text-input class="... @error(...) ... @enderror">` puts the literal text into the class list). Inside component attributes use echo syntax instead: `{{ $errors->has('field') ? '!border-red-500' : '' }}`. Directives are fine in plain HTML elements and inside component templates/slots.

**One visual form language (every form, TWO tracks only):** required fields show a red `*` in the label; a field with an error gets a RED BORDER plus a red message directly below it. Tracks: (1) **AJAX/Alpine modals** → `x-crud.form-field` (wrapper `crud-field-error` paints the border, Alpine `formErrors` drives it); (2) **server-rendered plain-POST forms** (auth pages AND profile) → `x-auth.form-field` (supports `bag`, `value`, `id` props; error logic lives inside the component template). Any new form picks the track matching how it submits — never invent a third look, and never put error logic in a component-tag attribute (see Blade gotcha).

**Frontend guards:** every AJAX action needs an in-flight flag (`saving`/`deleting`/...) with a disabled binding; plain forms are covered globally by `resources/js/form-guard.js`. Every form gets client-side validation via `resources/js/validate.js` mirroring the backend rules — the backend stays the source of truth.

**Cascade delete (owner's rule):** deleting a user hard-deletes everything they created, recursively — their user subtree, their created roles (unless still assigned to a surviving user), and their created stores (soft-deleted). Implemented in `User::deleteCascade()`; every entity creation must set `created_by` so the cascade can find it. NO soft-delete for users, by explicit owner decision.

**Activity logging:** every mutation endpoint calls `ActivityLog::record()` (action like `user.created`, subject, human description). When adding a new mutation endpoint, add its log line in the same commit. For actions performed while unauthenticated (e.g. password reset via email link), pass the acting user explicitly as `record()`'s fourth `$actor` argument. Deliberately NOT logged (owner-accepted noise/no-op exclusions): failed login attempts, forgot-password link requests, `confirm-password` (session-only), and the unused email-verification resend. The log page is gated by `activity-view`.

**Testing:** new interactive elements get `dusk="..."` selectors; browser flows run under Dusk against the throwaway `dusk.sqlite` env (see `.env.dusk` / `phpunit.dusk.xml`; never point Dusk at a real database). When each suite must pass is defined once in Definition of Done (`06`).
