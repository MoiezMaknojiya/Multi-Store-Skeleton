# Project Conventions

Enforce on EVERY change — and when fixing a gap, sweep the whole class of it project-wide, not just the reported instance.

**Organization, everywhere (owner, 2026-10-01 — "store change kar k organization kar du? ... hospital aur education like school aur bhi dusre institue ko bhi sell kar saku", then "ab haar jagha organization kardo, Database mein aur jaha jaha bhi store use huwa ha usko organization kardo"):** the tenant is an **organization** in every word a person reads and in the code and the database alike — tables and columns (`organizations`, `organization_user`, `organization_id`), models and services (`Organization`, `OrganizationTeam`, `OrganizationStorage`), routes and URLs (`/organizations`, `/settings/organization`, `organization.switch`), the session key (`current_organization_id`), permission names (`organization-view` …), logged actions (`organization.created`), `dusk` names and JSON keys. A new word, name or key says organization, never store or shop. What stays "store": the word meaning *save* — a resource's `store` action and its route name (`media.store`), the `{resource}-store` create permissions (`media-store`, and `organization-store` for creating an organization), `StoreMediaRequest`, `MediaStorage::store`, Laravel's `storeAs` and cache store, Alpine's `$store`, the player's local-storage helper. The databases that existed were renamed in place on 2026-10-01 (tables, columns, indexes, keys, the four permissions, the logged actions and the `Organization` subject), and the migrations have said organization from their first line since (see **Migrations** below). `OrganizationWordsTest` fails on "store" or "shop" anywhere a page lets a person read it, and `MigrationsTest` on a table, column, index or migration file named after a store — **a new page joins the first one's lists.**

**Migrations — one file per table (owner, 2026-10-01 — "itni sari migration ki file ban gae ha, isko kum kar sakte ha? har table ki ek, jese hum fresh kaam shuru karte ha"):** `database/migrations` is Laravel's own three files (users with password resets and sessions, cache, jobs), one `create_{table}_table` file for every other table, in an order the foreign keys allow, and `2026_10_01_202300_insert_permissions_and_starter_roles` — 26 files that build exactly what the forty before them had built (proved table by table on MySQL: against a build from the old files, against the live database and against the owner's own). A database the old files built has every table already, so **each file leaves a table that is there alone** (`Schema::hasTable` first; the last file skips a catalogue that exists, and forgets the old files' rows in `migrations`). Which is why **a file here is never edited to change a database that exists — that database would skip it: a new column, index, table or permission is a NEW migration**, reversible, and a new table gets a `create_{table}_table` file of its own. `activity_logs` partitions itself by year on MySQL inside its own file. The first change since is one: `2026_10_02_100000_put_the_time_on_the_schedule_rule` (the dayparts go, see **Schedules**) — the two daypart tables' create files stay beside it until every database has run it, as the files it follows did. `MigrationsTest` holds it: a file per table, nothing named after a store, every file harmless on a database that has its tables, the catalogue kept, and the whole set rolled back and forward. Every parameter in `database/migrations` carries its type, a closure's too (`MigrationParametersAreTypedTest`, which reads the files as PHP tokens). A dump taken before 2026-10-01 22:39 UTC still says `stores`: it is brought forward with the code of commit `0eb3740`, which carries the rename, before any later one (deploy/README.md).

**Authorization model — the organization (docs/ORGANIZATION-SPEC.md is the source of truth):** power comes from **membership** alone — an `organization_user` row `(user_id, organization_id, role_id)`, one role per person per organization — never from who created whom. Nobody owns an account: there is no `users.created_by`, no admin sets or knows another person's password, and a person's name, phone, email and password change only from their own Profile or "forgot password". Two tiers, mutually exclusive — a platform account is never an organization member and an organization member never holds a platform role (accepting an invitation, the owner email of a new organization and platform invitations all refuse the other tier; joining by invitation, `InvitationResponseController::join`, and the platform's Users → Organizations add, inside `OrganizationTeam::changeTeam`, ask it again after their lock on the person's row with `User::isOnThePlatformTeamNow()` — a plain read, never `globalRole()`'s per-request memo, and never a locking read of `organization_user`, whose shared gap locks let two assigns deadlock — so an invitation accepted at the same moment is seen and one account never holds both):
- **Platform** = a membership on the sentinel `organization_id = 0` holding a global role (`User::globalRole()`). It works above the organizations — every organization, every account — limited to its role's permissions. **Super-Admin** is the role named `Super-Admin` there. **A super admin holds every permission** (owner's rule, 2026-09-16: "sab matlab sab"): a `Gate::before` in `AppServiceProvider` answers yes to every permission check whatever the role's rows say — a permission made later, or renamed, included. It answers permission checks only: rules that are not permissions still stand (the primary's protection, Super-Admin never changed and the Owner role never deleted, an organization's last Owner, a super admin never deleting themselves), and `network-ads-toggle` — a place ("inside an organization, logged in as one of its people"), not a permission — keeps its own test. Only super admins make the organization roles and the platform roles (see **Roles**), look after every organization's custom roles from the platform (the Roles page lists them in a card of their own), put anybody in any organization with a role, change that role or take them out (Users page → **Organizations**, owner's rule 2026-09-17: `UserController::organizationAccess`/`assignToOrganization`/`changeOrganizationRole`/`removeFromOrganization` — straight in, nobody invited; a role that organization has; never a platform account; the organization keeps an Owner; taking someone out asks for the password), invite platform staff, remove a platform role, "Log in as" and reach the permission catalogue. **"Log in as"** keeps two session keys (`ImpersonateController::SESSION_KEYS`: who to return to, and whom they view as), written after the impersonation's own login; every sign-in clears them (a `Login` listener in `AppServiceProvider`) and "stop" works only for the account being viewed as — a session whose impersonated account was deleted mid-way once handed the super admin to the next person who signed in on that browser. The **primary** super admin (`User::primarySuperAdminId()`, the first Super-Admin membership) alone may take Super-Admin from someone or delete a super admin account, and nobody may act on the primary.
- **Organization** = memberships in real organizations. Permissions are read against the membership of `session('current_organization_id')` (`User::contextPermissionNames()`; a platform role always wins over a stale organization left in the session). **A person of one organization works in it from their first request** (`ChooseTheOnlyOrganization`, in the web group; QA round, 2026-10-09: an Owner who signed in from a link and landed on a screen was told "Your role does not allow it"), an organization the session names that they are no longer in is forgotten, and somebody with several, none chosen, who opens a page is sent to the chooser rather than refused (`bootstrap/app.php`), which returns them to that page (`OrganizationController::switch`, `redirect()->intended`). A test of "no organization chosen" uses a person of two organizations (`inASecondOrganization()` in `tests/Pest.php`). Holding a permission in organization A grants nothing in organization B. An organization's role may also carry the platform permissions that can work inside one organization, and there they reach that organization alone (see **Platform permissions**). **An organization the platform pauses** (its Active switch off, `organizations.is_active`; owner, 2026-09-30) is closed to its own people: `EnsureOrganizationIsActive` (`organization.active`, on every route of the signed-in panel and on the uploads) sends a page to the dashboard, which says "{organization} is paused" (`dashboard/partials/paused.blade.php`), and refuses a request a page makes with the same words (403); their role there grants nothing meanwhile (`User::pausedOrganization()` inside `contextPermissionNames`), so no page offers what would be refused; switching to another of their organizations (`organization.switch`), leaving it, answering an invitation to another on the dashboard and their own profile stay open. "Log In As" one of them shows the same page. The platform is never stopped by it — it looks after the organization and turns it back on from the Organizations page ("Off pauses the organization") — and the organization's screens keep playing: the device API is not behind it (the owner has not asked for a paused organization's televisions to stop). Pausing and turning back on are logged as `organization.paused`/`organization.resumed`; an organization's own people can never switch it (Settings → Organizations ignores `is_active`). A new signed-in route joins that group — `PausedOrganizationAttackTest` walks every one.

**A role does not matter — its permissions do (owner's rule, 2026-09-17: "role matter nahi karta, permission matter karta ha"):** whatever a role is called, what its holders may do is exactly what its permissions allow, and a page shows exactly those buttons and links. No rule asks "is this person an Owner?" to allow an action; the Owner role's only special standing is below. The super admin decides who holds which permission and takes care that a role gets nothing that could break an organization.

**Roles — no built-in roles but Super-Admin (owner's rules, 2026-09-17):** the super admin makes a role and says what it is for. **Organization roles** (`is_global = false`, `organization_id` NULL) are made on the platform's Roles page with "Organization role" and are offered in EVERY organization; the super admin renames them and changes what they allow (every organization at once, `RoleController::update`); inside an organization they are read-only. **Delete** is offered on every role but Super-Admin and the Owner role — a role somebody still holds is refused with **"Please unassign {role} from everyone first: {n} person still holds it."** (the Roles page says it as a toast at once, before any password; `RoleController::destroy` refuses it again with a 422, and once more under its locks, taken in the order every change that gives a role takes them — a custom role's organization row, the invitations to the role by id, row by row, then the role itself — its holders counted with a shared-lock read, `RoleController::refuseWhileHeld`: somebody given the role while the password was typed is seen and keeps it, never taken away by the cascade). **The Owner role** is the organization role marked `roles.key = 'owner'` (`Role::OWNER`, `Role::owner()`, `Role::isOwner()` — never found by its name): its holders are the organization's owners — an organization may have several (partners) — "at least one Owner" counts it, public signup, owner invitations and Create organization give it, and an organization changes hands by giving it on the Members page. It is renamed and changed like any organization role but never deleted. **Platform** roles (`is_global = true`) are made with "Platform role", for the team above the organizations. What a role is for is fixed once it exists. **Custom** roles (`organization_id` = the organization) are an organization's own, made on its Roles page: any member holding `role-update`/`role-destroy` manages them within reach whoever created them, a super admin manages every one from the platform, they survive their creator, and one still held cannot be deleted. `Role::STARTERS` (Owner, Admin, Staff, Viewer — keys `owner`/`admin`/`staff`/`viewer`) is only where an installation begins: one migration inserts the permission catalogue and all four roles (`2026_10_01_202300_insert_permissions_and_starter_roles`) and the seeder only puts the Owner role back should it be missing — neither ever touches an existing role, so a re-seed cannot undo the super admin's changes or bring back a role they deleted; a starter key gives no power. Owner and Admin start with every organization permission and View Organizations; Delete Organizations starts with the Owner role alone. A name must be new to every list the role is shown in (`RoleController::validated`), compared with accents, case, spacing and punctuation folded away: an organization role against every organization role and every organization's custom roles (it is listed in all of them), a custom role against its organization's list, a platform role against the platform roles, and nothing may be named like Super-Admin. A role of another organization is never usable here (`Role::availableInOrganization`: 422 on `role_id` when inviting, assigning or changing a role, 404 on the Roles endpoints). (The migrations that upgraded the owner's own database to this model — the people conversion, the merge of same-named organization roles, the organization-transfer permission and its removal — were squashed away on 2026-09-17, and every change since on 2026-10-01: `database/migrations` builds the final schema and the starter data directly, one file per table — see **Migrations**.) **The Super-Admin anchor is the exact name compared in PHP (`Role::SUPER_ADMIN`, `Role::superAdminId()`, `User::isSuperAdmin()`), never a `WHERE name = 'Super-Admin'`:** MySQL's `utf8mb4_0900_ai_ci` collation reads "Súper-Admin" as that very name, so a SQL comparison let a look-alike custom role make every holder a super admin.

**Hierarchy (one place: `App\Services\OrganizationTeam`):** to **assign** a role (invite, change role) it must be available in the organization and the actor must hold every permission of it in this organization (`mayAssign`). To **manage** an existing member (change role, remove) it must not be yourself and the actor must hold every permission of the member's current role (`mayManage`). Both compare permissions only (`roleIsWithinReach`) — the Owner role is given and managed like any other, by whoever holds everything it allows (owner's choice, 2026-09-17). Because an Owner can be reached by somebody who is not one, the last-Owner rule below is checked on its own in every change or removal of a member (Members page `MemberController::update`/`refuseTheLastOwner`, Users → Organizations), and a row never offers it (`can_manage` is false on an organization's only Owner). **At least one Owner, always:** the last Owner cannot be demoted, removed, leave, or delete their account — and every change that could break that is decided under the organization row's lock (`OrganizationTeam::changeTeam`, and for an account's own deletion `OrganizationTeam::whileTheirOrganizationsAreLocked`), reading the owners INSIDE the lock, so two co-owners acting at the same moment cannot both pass. `changeTeam` answers 404 when the organization row it locks is gone (`firstOrFail`), so no membership of a deleted organization is ever written; a change that writes a person's id into a membership or an invitation passes that person as `naming:` (the member it puts in, the inviter an invitation records: Users → Organizations' add, the Members page's invite, Invite Owner), whose row is read next FOR SHARE, 404 when they are gone; and a change that gives a role passes it as `giving:` (Members → Change Role, Invite, Users → Organizations' add and change), read FOR SHARE after the person and refused "Choose a role that exists in this organization." when it is gone (a platform invitation reads its inviter and then its role the same way, "Choose a platform role.", `PlatformInvitationController::store`). **Locks are taken in one order, everywhere: organization, person, invitation, role** — an organization's row before a person's, and a membership row never locked before its organization's (`changeTeam`, an account's deletion, `accounts:prune-unverified`, an invitation's answer, `Organization::purgeContents`); a new path that locks two of them takes them in that order. `whileTheirOrganizationsAreLocked` locks EVERY organization the person is in, Owner or not, by id in id order, then their own row, both FOR UPDATE, as the transaction's first statements — which organizations is read before the transaction, since MySQL's REPEATABLE READ answers every plain read from the snapshot the first plain read took — and starts again with the newcomer locked too, up to three times (`LOOKS`), when the person was put in another organization while it waited; an account deleted meanwhile is 404. **Leaving** is open to every member: from the Members page, from "Your organizations" on Settings → Organizations, or — without View Organizations where they work — from "Your organizations" on the profile (`ProfileController::leaveOrganization` returns to the page it came from). An organization changes hands **on the Members page** (owner's rule, 2026-09-17 — there is no Transfer Ownership and no `organization-transfer` permission any more): whoever holds everything the Owner role allows gives it to another member with Change role, and the new Owner may then change the first one's role — the last-Owner rule keeps the organization from being left without one in between. The server sends what each row allows (`can_manage`, `assignable_roles`, `can`), so a page never offers what the controller would refuse — and the controller checks it again regardless.

**How people enter (nobody is created by somebody else):**
- **Public signup** (`/register`, routes/auth.php): a customer creates their account and their organization in one form and becomes its **Owner** — server-chosen (`Role::owner()`), never client input — and confirms their email before the panel opens (see **Email verification** below). **The form keeps robots out** (owner, 2026-09-30: made-up names signed up on the live site all day, each sending a confirmation email to somebody's real address): `<x-auth.robot-trap>` carries a `display:none` field no person meets (`website`) and the sealed (encrypted) moment the form was opened, and `RegisteredUserController::looksLikeARobot` sends the form back with "Please try again." — nothing written, logged or emailed — when the field is filled or, while `signage.signup_min_seconds` is above nought (3 by default, none under the test suites), the form came back sooner than that, with no sealed moment, a forged one or one older than `signup_form_lifetime_seconds` (two hours); `SignupRobotAttackTest` holds it. A robot that gets past both makes an account nobody confirms, which the 7-day prune takes.
- **Invitation** — from an organization's Members page (`member-invite`); from the platform when it creates an organization for a customer (`organization-store`: the owner's email gets an Owner invitation) or gives an ownerless organization an owner; and for platform staff (super admins). The 64-character token lives only in the email — the database keeps its SHA-256 hash (`invitations.token_hash`) — the link lasts `Invitation::LIFETIME_DAYS` (7), Resend rotates the token (`Invitation::renew`, under the invitation's own row lock: Resend on one revoked a moment ago is 404 and sends nothing) and Revoke deletes it. The link's page (`InvitationResponseController`) creates the account when none exists (marked verified: opening the link proved the inbox) and otherwise makes the person sign in first — **the link alone never logs anybody in** — and tells a person signed in with another email so. Answering an organization's invitation — the emailed link, the dashboard's Accept, or a new account made from the link — takes the organization's row first (`InvitationResponseController::lockItsOrganization`, the first statement of `join()` and `register()`), then the person's, then the invitation's, so a double submit or a second tab never uses one link twice and an accept and `Organization::purgeContents` queue at the organization row rather than deadlock: an organization deleted while the answer waited is said on the page it lands on ("{organization} has been deleted, so this invitation can no longer be used." on the dashboard, "no longer valid" on the link's page), the person's own account deleted meanwhile is 404 (`join()` reads that row with `firstOrFail`), and a decline at that moment deletes and logs nothing (`deleteDeclined`). The email goes out through `Invitation::sendLink()`, which reports a refusing mail server instead of throwing — the response says `email_sent: false` and the page shows it as an error, while the invitation stands for Resend. On the platform, **"Invite owner" is offered only for an organization with no Owner** (owner's rule, 2026-09-17): the row's `can.invite_owner` needs `organization-store` and an `owners_count` of 0, and `OrganizationController::inviteOwner` refuses an organization that has one (422, "{organization} already has an Owner.") — deciding everything inside `OrganizationTeam::changeTeam` (the Owner count, the member made Owner, the invitations retired, renewed or opened), so an Owner given meanwhile is refused in those words and an organization deleted after its address found it is 404, never a foreign-key 500 — more Owners come from the organization's own Members page, or Users → Organizations. A member of that organization is made Owner at once; anybody else is invited. The same address again sends a fresh link (expired or not), and a different address — or a member made Owner — retires the earlier owner invitations (`retireOwnerInvitations`), so a mistyped email stops working. Only the primary super admin invites a new super admin (the one who can also take it away). Both sides are throttled by named limiters (`invitations`, `invitation-response`). **The dashboard answers them too** (owner, 2026-10-07 — "haan bana do, decline par sirf log, dashboard card kaafi ha"): "Invitations for you" stands above every dashboard of an organization's person (`dashboard/partials/invitations.blade.php`), listing the organizations' invitations sent to their own address and still open (`Invitation::sentTo`, `stillOpen`) with Accept and Decline (`InvitationResponseController::acceptHere`/`declineHere`, their `{invitation}` an id an int can hold — `[1-9][0-9]{0,17}` in routes/web.php, see **Input gotcha — a query parameter can be ANY shape** — behind `verified` — every account now proves its inbox before the panel opens, which is what the emailed link proves): Accept is the link's own join (the tier rule, the row's lock, the welcome), Decline asks first, deletes the invitation and only logs it — nobody is emailed. Anybody else's invitation and the platform team's (answered by its emailed link alone) answer 404; one that expired on a page left open is said on the dashboard.
- **Email verification** (owner's rules, 2026-09-29 — "we will do email verification when anyone will create account", "no aliases, delete after 7 days"): signup sends a signed link (`VerifyEmailNotification`, `auth.verification.expire` minutes, naming the account by id and the address by `sha1`), and until it is opened the account stands behind `verified`: every page sends it to "Check your inbox" (`verification.notice`, a JSON request gets 403), and only its profile, the verification pages and links, accepting an invitation, its password, sign out and "stop" after "Log in as" stay open — `HttpSurfaceSweepTest` pins that list, so a new signed-in route outside `verified` fails until it is added on purpose. **A super admin who logs in as such an account confirms it there** (owner, 2026-10-06 — "waha ek button ho jo super admin ko hi show ho jis per click karne se email verify ho jaye aur agay chale jaye"): "Log In As" lands on "Check your inbox" — the Users page asks with axios, so `ImpersonateController::start` answers it `{redirect}` rather than a redirect its XHR would follow into the wall and read as a failure — and only then does the page show **Confirm Email and Continue**: `EmailVerificationController::confirmForThem` asks `ImpersonateController::superAdminViewingAs` again (both session keys, the account viewed, whoever started it still a super admin), confirms the email, logs `account.verified` naming the super admin, and opens the dashboard; the account itself, or a session that says anything else, is refused (403). A link opens nothing by itself (the account must be signed in) and a wrong one says why on the page it lands on (`EmailVerificationController::whyNot`). **One account per address, compared as typed** (no folding of dots or `+tags`). What came to the inbox confirms it too: accepting an invitation, and completing a password reset — which also ends every session of the account (`User::endEverySession`), so somebody who signed up with another person's address and kept a session open loses it the moment that person resets the password. Changing one's own password signs out every other device the same way (`Auth\PasswordController::update`: the `remember_token` rotated, this browser's remember-me cookie written again by `Auth::logoutOtherDevices`, and every session row but the current one deleted, `User::endEverySession(except: …)`); the browser that changed it stays signed in. And "forgot password" never throws a mail server's refusal (`PasswordResetLinkController::store` sends through `Password::sendResetLink`'s callback, `report()`s the failure and forgets the unsent token), so a real address answers exactly as an unknown one. **A confirmed account's change of email has two steps** (owner, 2026-10-15 — "email badalne per email verification ho jese sub karte ha"): the new address waits in `users.pending_email`, and an approval link goes first to the CURRENT address (`ApproveEmailChangeNotification`, `email.approve` behind `verified`, `EmailVerificationController::approveNewEmail`, which writes `users.pending_email_approved_at` — migration `2026_10_15_200000`); only then does `ConfirmNewEmailNotification` go to the new address (`email.confirm`), so an open session alone can never move the account to another inbox. `confirmNewEmail` refuses a change not approved (`User::approveFirstWords`: "Approve the change from {email} first. No email there? Press Send the Link Again below."), a new address typed on the Profile starts the approval over, Send the Link Again sends the link of whichever step stands (`User::sendEmailChangeLink`), and `approveNewEmail` asks `User::linkRefusal()` before it writes the approval, so a spent budget approves nothing and the link works again later. The old address stands meanwhile, the change can be given up at either step, and an address another account took in between is refused, never taken. Viewing as somebody through "Log In As", a change may be started — its links go to the person's own inboxes — but never approved or confirmed (`refusedWhileViewingAs`). An account not yet confirmed simply corrects its address at once, and the link goes to the new one — so nobody else may: viewed as through "Log In As", its email is read-only on the Profile and `ProfileController::update` refuses it ("Only {name} can correct their email, signed in themselves: not by Log In As.", `ProfileController::emailIsTheirsAlone`), and "Check your inbox" offers no "Wrong address?" link; otherwise Confirm Email and Continue and "forgot password" would hand the account over. A page or an email never says "we sent" a link a mail server may have refused: "Check your inbox" and the Profile say "Open the link in the email to …", and the Profile's two steps "No email? Press Send the Link Again." **Every email that confirms an address draws on one budget** — the signup's, "Send the link again" on either page, a new address typed on the profile (its approval) and the approval opened (the new address's link): 3 a minute and 20 an hour per account (`User::LINKS_PER_ACCOUNT`) and 30 an hour per visitor's IP across every account they make (`LINKS_PER_VISITOR`), counted inside `User::sendALink`, so no door can skip it; the profile asks `linkRefusal()` BEFORE it saves a new address, so a refusal leaves the account as it was ("Too many emails asked for. Try again in …", under the field or in the page's box — never a bare 429). And the three emails that confirm an address carry no text anybody typed but the recipient's own address — no name, and the approval's new address masked to its first character and its domain (`ApproveEmailChangeNotification::masked`): they go to whatever address a visitor types, and a name is where signup spam puts its words. Opening links is limited by the named `verification-link`. **An account never confirmed goes after `User::UNVERIFIED_DAYS` (7) days** with its organization (`accounts:prune-unverified`, daily at 03:15 by the server's existing scheduler cron): only when every organization of theirs is theirs alone and empty (`WHAT_AN_ORGANIZATION_HOLDS`), decided under the organization rows' lock and then the person's own — which organizations looked up before the transaction, the memberships read again under the locks, and an account put in another organization meanwhile kept for the next run (`PruneUnverifiedAccounts::handle`) — and the run names every account it keeps. The migration that brought the rule marked every account made before it as confirmed (one exact stamp, which its `down()` undoes), so nobody on the live site was locked out. The Profile's email status keys are in `components/toasts.blade.php`'s list, so none becomes a toast of its raw key.
- **No API:** this is a web-only app — there is no `routes/api.php` and no token API, by owner decision (a half-built mobile login was deleted 2026-09-03). Do not add API routes without explicit instruction; any future API needs validation, throttling, and tests from day one.

**Visibility & scoping:** inside an organization, `member-view` shows **every** member of the current organization (the viewer marked "You") and its pending invitations — never anybody outside it, never a platform account — an organization's people have no Accounts page of their own, the accounts pages are the platform's alone (`can:global-tier`, owner's rule 2026-09-17); `organization-view` on an organization's role opens the Organizations tab of Settings for the organization the person works in. On the platform a super admin sees every account — whole, or one side of it with the Users page's tabs, **All · Platform Team · Organization Members**, each saying how many it holds (owner, 2026-10-07: `group` read through `plainValue`, `counts` in the listing's answer; Organization Members is everybody outside the platform team) — and a platform user holding `user-view` sees organization accounts only, with no tabs and no counts. Account and Joined sort the list, newest first as it opens (`UserController::sortedBy`, `AccountTabsAndSortTest`). Every WRITE endpoint resolves its target inside where the actor stands: `ResolvesCurrentOrganization::currentOrganization()` (404 unless the session's organization exists and the actor is a member of it), `OrganizationTeam::roleOf()` (404 for somebody who is not a member), an invitation's `organization_id` against the current organization, a role through `Role::availableInOrganization`. Route middleware (`can:`) alone is NOT enough, and an id out of scope answers 404.

**Per-organization isolation (the organization is the wall):** whatever a member creates belongs to the organization they created it in — stamped from `session('current_organization_id')` on create — and every read and write of it lands in that same organization. With no organization selected an organization member sees nothing at all (an empty scope, not an unfiltered list). When adding any new organization-scoped entity: stamp it with the organization, add the same walls, and add it to `Organization::purgeContents()`, all in the same commit.

**Media library (organization inventory, not personal property):** a library belongs to an organization, or to the platform (docs/CHANNEL-CONTENT-SPEC.md, owner 2026-09-19). (3) **The server's own disk keeps its reserve** (owner's decision, 2026-09-29 — anybody with an inbox can make an organization, and the platform's library and the ads network have no wall of their own): `App\Services\DiskGuard::assertRoomFor` refuses an upload at every door — the Media page and a channel's Upload (`addToLibrary`), the shelf (`addBuilderAsset`), a campaign's file (`storeCampaignFile`) and a publish (`AdPublisher`, under `publish`), whoever uploads — once the disk would keep less than `signage.upload_reserve_bytes` (`SIGNAGE_UPLOAD_RESERVE_MB`, 5 GB by default, none under the test suites unless set): "The server is almost out of space, so uploads are paused for now. Please try again later: the team has been told." Every super admin gets `DiskAlmostFullNotification`, at most once in `DiskGuard::ALERT_HOURS` (6, a `Cache::add`), a mail server's refusal is reported and never thrown, and a system that cannot say what is free refuses nothing. A new upload door calls it before a byte is written. **Long before that the super admins are warned** (owner's rule, 2026-09-29: "server per jab 10gb khaali rahe toh email aye"): `php artisan disk:check`, scheduled every hour, emails `DiskSpaceLowNotification` while less than `signage.disk_warning_bytes` is free (`SIGNAGE_DISK_WARNING_MB`, 10 GB by default, none under the test suites unless set) — uploads still working — at most once in `DiskGuard::WARNING_HOURS` (24), and at once again after the disk has been above it in between. It looks on the clock, not at uploads, because a disk fills without an upload too: MySQL's binary logs (30 days by default, a line a minute per television from its heartbeat), the nightly backups, the logs. (4) **A picture is made light on its way in** (owner, 2026-10-05 — "upload par tasveer khud halki karne wala feature bana do, sub upload mein lagana aur yeh bhi dekhna k video bhi upload honti ha", "Badi tasveer ko chhota karna yeh bhi bana do"; docs/UPLOADS-SPEC.md §7): `App\Services\PictureOptimizer`, which `MediaStorage::put` asks at every door (the Media page, a channel's Upload, the shelf and the editor's picker, an advert, `builder:examples`), brings a JPEG, PNG or WebP over 4K down to 3840 px on its longer side (`MAX_EDGE`), turns a phone photo the way its EXIF says the camera was held, and writes a WebP — 85 for a JPEG, 90 for a PNG or a WebP, without loss for a palette PNG or a lossless WebP that kept its size — carrying the very colour profile it came with (an ICCP chunk after its VP8X header: an iPhone's Display P3 stays Display P3, which GD alone would drop). **Lossy WebP keeps colour at half resolution** — which a camera's JPEG has already done, but a PNG, a lossless WebP and a JPEG written at full colour (its frame header samples every component alike) have not — so such a picture is MEASURED (`losesColour`: the lossy WebP read back, 16×16 blocks, every other pixel, Cb/Cr moved by more than 24 in a tenth of a block, two such blocks) and written without loss when small coloured detail would change: on 33 real pictures (2026-10-05, the owner's question "tum ne sahi terha testing nahi ki") thin red words on black had turned maroon, and with the measure every picture with words (the owner's own menus, a 4K menu, a screenshot of the panel) came out pixel-identical in Chrome while 24 of 26 photographs and cut-outs stayed lossy (89% lighter); a picture whose lossless copy would be no lighter stays as it came. It is stored only when a tenth lighter (`MIN_SAVING`), or when it had to be brought down or turned, whatever it then weighs (WordPress's way with its own threshold); what is stored is what is counted to the 512 MB and sent to the televisions, and the answers of the Media page and the shelf carry `lighter: {from, to}`, which the row says as "Added · made lighter: 4.4 MB to 1.7 MB" when the two sizes read differently. Kept exactly as it came: a GIF, a PNG or WebP that moves, a CMYK JPEG, a colour profile that is not RGB (or a JPEG's, split across segments, with a part missing), a PNG whose gAMA or cHRM is not sRGB's and that has no sRGB chunk, a file not built as its format says (a JPEG with more than `MAX_JPEG_FILL_BYTES`, 4096, fill bytes in all among them — `PictureOptimizer::aboutJpeg` reads no more: one made of 250 MB of them held every picture upload on the server for a minute, read a byte at a time under the one picture's turn), whatever GD cannot read, and a picture that would not fit the request's memory (`fitsInMemory`, asked with everything GD holds on the way added up: a 48 MP photo takes some 280 MB of the server's 384; `makeImageThumbnail` asks it too, so a small file claiming a huge picture is stored with no preview, never a 500) — and a video, always (no ffmpeg). It never refuses an upload: whatever goes wrong, the file is stored as it came; the organization's wall and the server's reserve are asked with the size that came. **One picture at a time** (the owner, 2026-10-05: "break kar k dekha?" — six big pictures uploaded at the same moment on one CPU held 2.1 GB together, the live server's whole memory, because GD's copies and the WebP encoder's, which PHP's limit never sees, ran side by side): `MediaStorage::onePictureAtATime` makes one picture lighter and draws its thumbnail at a time on the server, under the operating system's lock on `storage/framework/cache/picture-turn.lock` (a request that dies hands it on at once); the six then hold some 590 MB and take about as long together, the first done in seconds; an upload whose turn has not come in `PICTURE_TURN_SECONDS` (90, so the wait and the work stay inside the two minutes `TakesAFinishedUpload` holds an upload) is stored as it came, the file its own preview, and a video never waits. A picture over 4K is brought down BEFORE it is turned, so a turn copies the smaller one (a 48 MP photo held upright did not fit the other way round). Brute force — 30 000 broken pictures, of which `PictureOptimizerAttackTest` keeps 200, broken the same way every run — found one 500: a header claiming two billion pixels a side overflowed the memory sum, which is reckoned as a float since. `signage.optimize_pictures` (`SIGNAGE_OPTIMIZE_PICTURES`) is on everywhere but the Pest suite, whose storage tests count files by the sizes they claim (`PictureOptimizerTest` turns it on); Dusk runs with it, so a browser test that compares bytes uploads a GIF.

**Uploads — dropped, sent in chunks, shown as they go (owner, 2026-09-29 — "drag and drop lagana ha chunking karni ha aur acha se progress bar dikhana ha"; docs/UPLOADS-SPEC.md):** every page that takes a file uses ONE uploader, `<x-upload-dropzone>` (`components/upload-dropzone.blade.php` + `resources/js/core/upload-dropzone.js`, Alpine `uploadDropzone`): a box a file is dropped on or chosen with, and a row per file with its preview, a bar, the speed and the time left, and Pause/Resume, Cancel and Try again — in the panel's own look. The bytes travel by tus 1.0 (creation + termination) through Uppy's ENGINE only (`@uppy/core`, `@uppy/tus`, MIT, loaded when a file is chosen — never Uppy's Dashboard), 5 MB a request, to the app's own endpoints (`UploadController`, `App\Services\ChunkedUploads`, the `SpeaksTus` middleware — no server package): `POST /uploads` opens an upload only after asking everything the finished file would be refused for (the permission and the place per purpose, the format by its name, the size, the organization's wall, counting every upload still on its way into it (a finished one is its door's to decide again), and every open upload into it, finished or not, at most its storage in all — so its people park no more than that on the server's disk ("Files uploaded for {organization} and not added yet already take its …. Add or remove them first, or try again later.") — both decided under the organization's lock (`ChunkedUploads::reservedInOrganization`), and the server's reserve counting every open upload's missing bytes; the type Upload-Metadata names is kept only as a plain type of at most the 100 characters `uploads.file_type` holds, `ChunkedUploads::typeOf`); `PATCH` writes a chunk at its offset under the row's lock (409 at another offset, 413 past the end); `HEAD` says how far it got; `DELETE` gives it up — never while a door is making its row from it: the box's × (`UploadController::destroy` → `ChunkedUploads::cancel`) answers 409 "This file is being added. Wait a moment." while the door holds `ChunkedUploads::finishLock` (`upload-finish:{id}`), and the others give way to it too, never waiting: `uploads:prune` leaves that upload for the door or its next run, and the TV app's inspect refuses on `file` with "This file is being added already. Wait a moment."; somebody else's upload is 404. The routes sit behind `auth`, `verified`, the named limiter `uploads` and CSRF. With every byte in, the page posts the door it always posted with `upload` (the id) in place of `file`: the four doors' Form Requests (`StoreMediaRequest`, `ChannelAdRequest`, `CampaignRequest`, `BuilderAssetRequest`) make it the request's `file` in `prepareForValidation` (`Concerns\TakesAFinishedUpload`: the person's own, finished, unexpired, opened for that door, one request at a time under `ChunkedUploads::finishLock`), so every rule — the format read from the bytes, a video's length from the file, the organization's wall, the reserve — runs exactly as for a file posted whole, and the controller forgets the upload once its row is made (`forgetFinishedUpload`). **A finished upload joins only the place it was opened for:** the dropzone decides the place once, at drop (`placeNow()`, kept on each row as `item.place`), and its key — `placeKey(meta)`, what the upload tells the server plus the page's session-context, "{user}:{organization}" — is part of the Uppy file id and the tus fingerprint (`meta.relativePath`), so a file cut short in one organization and dropped again in another is an upload of its own while a reload in the same one carries on; and the door refuses an upload posted for another organization than `uploads.organization_id` and gives it up ("This file was uploaded for another library/owner. Choose it again to add it here.", `TakesAFinishedUpload::assertUploadOpenedFor`, which the Media page, a channel's Add Ad and the shelf call). A file the rules refuse for what it is — its format, its size, a video's length or one nobody can measure, an APK that is not the TV app or not newer — is given up at once (`TakesAFinishedUpload::failedValidation` → `ChunkedUploads::refuseForGood`, whose answer says `upload_given_up`): its row shows the refusal with no Try Again, and in `form` mode the box sends `upload-cleared` `{givenUp: true}` so the page forgets the upload; a refusal room or time can fix keeps it for Try Again. A finished upload nobody posts lives `ChunkedUploads::FINISHED_LIFETIME_HOURS` (2) after its last byte (set in `ChunkedUploads::append`, never lengthening its day). **A form's box** (`mode="form"`) is found on the page by its `dusk` through `emptyTheBox` and `giveUpUpload` (`resources/js/core/form-asked.js`), never through `$refs` from outside the dialog — a ref inside `<x-modal>` belongs to the dialog; it is emptied every time its form opens and every time its dialog shuts, Escape and Discard Changes included (`$watch('show', (open) => open || clearFile())` on the box's listener inside the dialog), an upload nobody saved given up then; the upload a save carries (`uploadBeingSaved`) is never given up under it — the box is held, `inert`, while that save is out (`holdsTheSavedUpload`); and after a successful save or publish the box lets its row go without giving it up, `emptyTheBox(selector, savedUploadId)` — never the box's `clear()`, which gives up the upload the server just used (campaigns, a channel's Add Ad, Developer → TV App's `startAgain`). **A new upload door does all three:** its request takes the trait, its controller forgets, its page uses `<x-upload-dropzone>` — and a door whose page can change its place calls `assertUploadOpenedFor`. Two modes: `add` (the Media page and the shelf, the box on the page itself, and the Ad Builder editor's picker — several files, each posted as it arrives, titled by its name; its "Added" row fades away after eight seconds, as a notification does — `ADDED_STAYS_MS`, owner 2026-09-30 — while "3 of 5 added" still counts it until nothing is going any more, and a refused or failed row stays for its reason) and `form` (a channel's Upload, a campaign's advert — one file; Save waits for it, `upload-busy`). A page listens for the box's events on an element of its OWN around it (the Alpine gotcha below). The parts are `{id}.part` on the `uploads` disk, a root per environment as `public` has (`storage/app/private/uploads`, `dusk-uploads`, `framework/testing/uploads`), because `uploads:prune` — hourly: an unfinished upload after 24 hours, a finished one never posted after two, a part no row names and a TV app file left under its incoming name after an hour — must never see another database's parts; `DuskTestCase` sweeps a test's own. A connection that fails is tried again for some 25 minutes (`RETRY_DELAYS`), an offline browser waits and carries on the moment it is back, a request silent for 30 seconds is sent again, the bar never goes back, and a page left mid-upload asks first. The browser still checks what it can before a byte (`fileError`, `storageError`, `videoLengthError`); the server decides.

**Screens & the device API (the one machine-facing surface):** a TV has no session, so `routes/device.php` is registered OUTSIDE the `web` group — no cookies, no CSRF, four endpoints only (`register`, `pair-status`, `playlist`, `heartbeat`). Deliberately NOT `routes/api.php`: the owner's no-API rule stands, this is a narrow device channel with its own stateless stack. Rules that must hold together: **open ≠ unauthenticated** — `register` is open but throttled 30/min per IP, `pair-status` is open but demands the `poll_secret` issued at registration (so a guessed uuid cannot steal a freshly minted token), and everything returning real content sits behind `device.token`. A screen's identity is a 64-char random token **stored only as a SHA-256 hash** and handed to the device exactly once, on its first successful poll, after which the `pairing_requests` row is destroyed. Pairing codes are 6 characters from an alphabet with no `I/O/0/1` (read off a TV across a room), live 15 minutes, and are created only when a player actually opens — so there is nothing to clean up but strays. `screens.organization_id` follows the media wall: stamped from `session('current_organization_id')` at pairing — or, above the organizations, from the organization chosen in the Add Screen dialog's Organization list (owner, 2026-10-05: the platform had the button and nowhere to say whose screen it was; `organization_id`, required there and read from nobody else, `ScreenController::pairingOrganizationId`), where the list says whose each screen is, `Screen::visibleTo` scopes on the organization alone, and a screen from another organization 404s. Re-pairing an existing screen rotates its token in place (old device locked out on its next request, playlist and settings kept) instead of creating a second row. **`DevicePairing::claim()` looks the row up INSIDE its transaction with `lockForUpdate()`** — a code answers to exactly one screen, and reading it unlocked let two people (two staff, two tabs, a retried request) both be told "screen added" while only one token can be stored, leaving the loser with a screen whose token nobody holds: permanently offline, and silent about why. **A uuid is no secret** (the panel lists every screen's): `DevicePairing::register` gives a waiting request's code back only to the caller holding that request's poll secret, and anyone else gets a request of their own (a new uuid, code and secret); a claimed request whose token is not yet collected is never wiped, its row read under its lock, and only a code that expired unclaimed starts over under the same uuid; the player (`startPairing`/`askPairStatus` in `resources/js/player.js`) asks `pair-status` with the secret it holds before it registers again. A uuid that has no row is never read under a lock (`DevicePairing::registerOnce` — on MySQL a locking read of a missing key holds the gap it would go in, and two registers holding one gap deadlocked on their inserts): it is looked for before the transaction and inserted at once, and a second register of it at the same moment meets the unique key and finds the row on its next try (`REGISTER_ATTEMPTS`, 3). Deleting a screen is how you revoke a device: it gets 401 and falls back to showing a fresh code. **Every throttle on this app uses a NAMED limiter (`AppServiceProvider::registerRateLimiters`), never the bare `throttle:n,1` form.** That form keys on domain+IP alone for a request with no logged-in user — the route is NOT part of the key — so every route using it shares one counter per visitor. An organization's TVs and the owner's laptop share one public IP, and each paired screen sends three requests a minute, so the bare form let a handful of screens exhaust the signup form's budget and lock a new TV out of pairing while the running screens hid the problem. The device limiters therefore count PER DEVICE (`device-api` by token hash, `device-pair` by `device_uuid`, each with a looser per-IP ceiling); only `device-register` keys on IP, because a screen asking for its first code has nothing else to be known by. `throttle:device-api` also runs BEFORE `device.token`, so a wrong token is rate limited too. **The limiters count in the database cache, whose deadlock victims are run again** (owner, 2026-10-14: live logged a 1213 on `insert ignore into cache … :timer` about once a day — an organization's televisions share the per-address rows): the `database` store's driver is `database-retrying` (`App\Cache\DeadlockRetryingDatabaseStore`, registered in `AppServiceProvider::register`), which runs a call again up to three times on a deadlock alone — never on a lock-wait timeout, never inside a transaction the caller opened — as MySQL's manual asks; on MySQL, 24 processes on one key gave 165–178 deadlocks with Laravel's own store and none with it, every hit counted (`CacheDeadlockTest`). Never move the limiters to the `file` store to be rid of it: a file's increment is a read and a write apart, so a burst of wrong passwords would be undercounted. **The player is a progressive web app that keeps playing offline** (docs/AD-BUILDER-SPEC.md §15, owner 2026-09-23): `public/player-sw.js` — plain ES5 at a fixed address, never built by Vite, registered at scope `/player` so the panel is never served from a cache — keeps four caches. The **shell**: the page (network first) and the built files it names, kept together or not at all, so a set rebooting with no line never has a page whose scripts are missing (the page's inline watchdog reloads one whose script never ran). The **manifest**: the last `/device/playlist` answer PER SCREEN (keyed by a digest of the token, never the token), network first with an 8 s patience — a 401 goes through untouched; only an unreachable server, a 5xx or an answer that is not JSON (a captive portal) falls back to it, marked `X-Signage-Cached`; a late answer is kept anyway. The **media**: every file by VERSIONED address, matched exactly (`assetUrl()` appends `?c=checksum`, the runtime carries `?v=`; with no line and no copy of that version, the same file's previous one plays instead). The **parts**: a big file fetched 4 MB at a time by range requests, so a download cut short carries on. ONE warm-up, however often the player asks: one file at a time, most needed first, files and the runtime only and never with cookies, then the prune, which keeps an older version until the named one is in. The manifest carries `fallback` (the holding picture) and a **`timeline`** — what the screen shows at every moment its answer changes over the next 72 hours (a rule's hours and days, a line's dates, campaign windows), worked out by the same resolvers that answer online — which is also every file the player warms: nothing further off reaches the device. An Ad Builder page plays in a frame opened at `/player/page?src=…`, inside the worker's scope (so what it loads comes from the cache on every browser with a worker — a `srcdoc` frame is a worker's client only from Chrome 135), `sandbox="allow-scripts allow-same-origin"` — a frame with an origin of its own is served by no worker — and the page carries its own Content-Security-Policy (`AdCompiler::contentSecurityPolicy`: inline scripts by digest, the runtime's folder, no request, form, frame, plugin or base of its own); with no worker the page plays straight from the server with `allow-scripts` alone. `php artisan builder:recompile` writes every published page again from the version on the screens (never the draft), and every deploy runs it with `--outdated` after the site has switched over (`deploy/server/release.sh`): each page's head names the compiler that wrote it (`AdCompiler::VERSION`), and only pages an older compiler wrote are written again — so **move `AdCompiler::VERSION` whenever what the compiler writes changes in a way the published pages should get too**, or they keep the old output. Offline, the player plays the timeline's entry for now (past its end, the last one) by its own clock corrected by the last live `server_time` (kept across reboots, never earlier than the manifest) — the server already put the holding picture in every entry with nothing else due, or left it black; the loop restarts only when what would be shown changes. Heartbeat, register and pair-status are never cached: a heartbeat that cannot get out is what tells the panel a screen is offline, and nothing on the television says so (owner's rule). A new file kind a screen plays must reach the timeline's `lines` and use `assetUrl()`; a new device endpoint must decide whether the worker may cache it. **And it runs on old WebViews** (owner, 2026-09-24): a Fire TV, a cheap Android box and the Android player app (`com.thedisplaysolution.player`, `com.digitallifts.player` before 2026-10-04, its own project outside this repo) may carry a WebView as old as Chrome 80, so the player page loads no stylesheet but its own (Tailwind v4 needs Chrome 111; the few reset rules it relied on, `[hidden]` among them, are written in its `<style>`), uses no CSS that floor lacks (`inset` is Chrome 87), Vite writes the syntax down to `chrome80` (`build.target` in `vite.config.js`; the stylesheets keep Vite's default, so the panel's CSS is unchanged) and nothing a television runs — the player's script, its worker, the ad runtime — calls a newer API. `PlayerOnOldWebViewsTest` holds all four, and the Android app blames the WebView only below the same floor.

**A network break comes between two items, never in the middle of one (owner, 2026-10-23 — "jese hi ad khatam ho toh hamari network ads chale", asked and chosen: the ad on screen, not the whole channel):** a break that comes due while a picture, a video, an Ad Builder page or a channel's ad is on screen waits for it to end (`state.ad.due`), plays its adverts there (`breakBetweenItems`, from `advance()`), and the next item comes on after them from its start (`endAdBreak`, `between`). It waits one item at most; only an item still on screen `BREAK_WAIT_SLACK_MS` (15 s) past its own end — a video whose length reads wrong, one that stalls — is paused under the break and carries on from where it stopped (`waitForTheItemOnScreen`, `pauseContent`/`resumeContent`). A poll meanwhile leaves the waiting break as it is (`armAdBreak`), and a screen gone dark meanwhile waits for the next break. `NetworkAdBreakTest` holds it, seen failing on the player before.

**A video on a portrait Fire TV: the app turns the display, the page turns nothing (Roadstar 4, 2026-10-27/28 — found on the owner's own Fire TV Stick 4K Max over adb, `dumpsys SurfaceFlinger` every two seconds beside `screencap`):** a `<video>` starts on the WebView's compositor, where the stage's CSS turn applies and it is upright, and a few seconds later Chromium promotes it to a hardware overlay — an HWC layer `SurfaceView - …MainActivity`, Comp Type Device — whose box is the element's UN-turned layout rect clipped to the viewport (logical 1080×1080 at the top-left) and which no CSS transform reaches: sideways, small, a black bar, until the element is replaced. Which is why replaying it in place made it sideways all the time, why the cycle followed the poll, and why taking it off the plane (`opacity: .999`, a canvas) showed black or nothing; those three changes went live that night and were all rolled back (`03407bc` … `3f2982b`, reverted in `ecc5268`). Turning the DISPLAY at the OS level works on Fire OS (`settings put system user_rotation 1` made it 1080×1920) and the HWC turns the overlay plane with it: with the page drawing the screen flat, the video was upright and full-screen in every moment, overlay and compositor alike. So the fix has two halves. **The page's half (done):** the quarter turns of `#stage[data-orientation="portrait"|"portrait_flipped"]` live inside `@media (orientation: landscape)` in `player/index.blade.php`; on a viewport taller than wide the stage is the viewport and nothing is turned (`PlayerStageTurnTest`, `TurnedDisplayTest`). **The app's half (its own project, not in this repo):** for a Portrait screen the Android player app requests `SCREEN_ORIENTATION_PORTRAIT`, for Portrait (flipped) `REVERSE_PORTRAIT`, reading the orientation from the page (`#stage`'s `data-orientation`, or a bridge the app adds) — until it ships, a portrait Fire TV keeps today's picture. A set mounted upside down (`landscape_flipped`) is still turned by the page, 180°, and its video has the same plane problem; the app's `REVERSE_LANDSCAPE` would fix it the same way once the page can be told the display is turned. Nothing for this goes live without being seen on a real Fire Stick first (the emulator has no Amazon WebView): the owner's stick, `adb connect`, `dumpsys SurfaceFlinger` — its "Display 0 HWC layers" table (Comp Type, Disp Frame, Source Crop) tells overlay from compositor at a glance — and `screencap` while it plays.

**Playlists (the thing a screen actually plays):** `playlist_items` is an ordered list of lines — each one a file `(media_id, duration_seconds)` or a channel `(channel_id)`, exactly one of the two (see **Channels**) — written by **replacing the whole list in one PUT** rather than patching positions — reorder, retime, add and remove are then the same call, it is atomic, and a half-finished rearrangement never reaches a TV. Three rules that must hold together: a screen may only play **its own organization's** files — never the platform's library (2026-10-07: it reaches a screen inside a platform channel) and never another organization's (`Media::playableOn`, `PlaylistController::assertMediaBelongsToTheSameOrganization`, 422 otherwise, naming a platform file — the organization wall in the one place it is easy to forget); the **schedule is resolved server-side** in `DeviceController::playlist`, so a line its rules keep off the air never reaches the device and a cheap box with a wrong clock still shows the right thing — a file keeps its name alone, with no dates or description of its own (owner, 2026-10-01: "srif naam rakho"; the Media page's Rename), and when it plays is its line's rules alone; and every manifest item carries a **`checksum`** — a cache key that moves only when the bytes may have, not a content digest: a picture's or a video's is the file itself (id, size, path — every upload is a new file with a name of its own, so a new title sends no television to download it again); an ad page, rewritten in place on every publish, adds its row's stamp; a channel ad's is its file's own (one file on a playlist and in a channel is one copy on the set), a campaign's is its file (`Media::cacheKey()`, `ChannelAd::cacheKey()`, `Campaign::cacheKey()`) — so the player's worker, or a future native shell, can decide whether the copy it already has is current. Reading a playlist is `screen-view`; WRITING one is `screen-playlist`, which also gates the picker's own media endpoint so it never drags in `media-view` (see **Capability-complete permissions**). Deleting a file cascades it off every screen it was playing on. **A save carries a `version`** — `Screen::playlistFingerprint()`, a content hash handed out by the GET and required by the PUT — and a mismatch is a **409**, never a silent overwrite — compared with the fingerprint read under the screen's row lock (`PlaylistController::holdScreens`, after the lines' own rows, see **Channels** (6)): 409 when it differs, 404 when the screen is gone, and Copy to Other Screens holds the source and every target the same way, in id order. Replacing the lines (a delete, then inserts) can still meet a neighbouring screen's save in MySQL's gap locks, so `PlaylistController::inTurn` runs the save and the copy again, up to `WRITE_ATTEMPTS` (3), for a deadlock (1213, `DeadlockRetryingDatabaseStore::isADeadlock`) and never for a lock-wait timeout. A file or a channel deleted while a save is on its way is found under the same lock and refused with a reason (422), never left to the foreign key's 500. Because the PUT replaces the WHOLE list, a client working from a stale copy would otherwise erase whatever a colleague changed in between with nothing to show for it; the fingerprint is content-based so re-saving an identical list is not a conflict, and the PUT returns the NEW version so one page can save twice. Nothing polls for it — it travels with the save that was already happening, so this needs no websockets.

**Schedules — the time is on the rule (owner, 2026-10-01 — "dayparts ko hata k kahi Playlist mein jab schedule set karte ha waha nahi dal sakte?", then "theek ha kardo"; docs/SCHEDULE-SPEC.md §21):** a line's schedule rule says WHICH DAYS (every day, between dates, or a repeat) and WHAT TIME — the whole day, or from one clock time to another, typed in the schedule window itself: `schedule_rules.start_time`/`end_time`, both or neither (`PlaylistController::ruleRules`, "Time: give both a start and an end, or choose All day."), never equal, an end before the start running past midnight and belonging to the day it OPENED on (`ScheduleRule::coversAt`, `openWindowDay`: half past midnight on Saturday is Friday's night). **Blade gotcha — `@json` in an `x-data` attribute (caused a real bug):** `@json` encodes with NO flags, so its quotes stay raw and the first string in the payload closes the surrounding `x-data="…"` attribute — Alpine then receives half an expression and the whole component silently fails to initialise (`items is not defined`, an empty table, no error page). Booleans and ints are safe, which is why every earlier page got away with it. Anything carrying a string or an array must use **`{{ Js::from([...]) }}`** instead, which hex-escapes for exactly this position; pass the whole config object through one `Js::from` rather than mixing the two.

**Blade gotcha (caused a real bug):** `@error`/`@if` directives do NOT compile inside a Blade COMPONENT tag's attributes (`<x-text-input class="... @error(...) ... @enderror">` puts the literal text into the class list). Inside component attributes use echo syntax instead: `{{ $errors->has('field') ? '!border-red-500' : '' }}`. Directives are fine in plain HTML elements and inside component templates/slots.

**Blade gotcha — one `@php` form per file (caused a real bug):** Blade lifts `@php … @endphp` blocks out BEFORE anything else is compiled, matching from the first `@php` it finds — so a file that already uses the inline `@php($x = …)` form and then adds a block reads everything between the two as one PHP block, and every page including it dies with a parse error (the sidebar once took down every page). Keep to one form in a file, and never write those words inside a Blade comment either — comments are stripped after the blocks are lifted.

**Validation gotcha — a validated array's ORDER is not the client's order (caused a real bug):** `$request->validate()` rebuilds nested wildcard data RULE BY RULE, not row by row: for `items.*.media_id` it sets every row that HAS a media_id, then for `items.*.channel_id` every row that has one. A row missing the first key is therefore inserted into the result AFTER rows that have it, so `array_values($validated['items'])` reads a different order than the client sent — a playlist saved "channel first, poster second" reached the television the other way round, and only a browser test caught it (backend tests had sent the kinds in the lucky order). The keys are still the client's indexes, so anything that cares about order must `ksort()` first (see `PlaylistController::writeItems`) — never trust the array's own order when rows can have different shapes. For the same reason, ids are validated `min:1`: a posted `0` reads as "no id" to `filled()`/`->filter()` and would sail past the ownership checks into a foreign-key error.

**Alpine gotcha — no getters in `extraState`/`extraMethods` (caused a real bug):** `createCrudTable` merges both with object spread (`...extraMethods`), and spread READS a getter instead of copying the accessor. A `get allOnPageSelected() { return this.items.length … }` therefore runs at merge time, with `this` bound to the plain literal rather than the Alpine component — `this.items` is undefined, it throws, and the whole `xxxTable()` call dies before Alpine ever evaluates the `x-data`. The page then renders with an empty table and EVERY binding on it reporting "not defined", including bindings that have nothing to do with the new code. Write a plain method and call it with `()` from the view; getters are only safe in `crud-table-base.js`'s own object literal (see `endItem`), which is never spread.

**Alpine gotcha — an object with private fields never goes into a component's state (caused a real bug):** Alpine wraps its data in a Proxy, and a class's `#private` fields cannot be read through one — Uppy kept in a component's data answered every file with "This file could not be sent". Keep such an object in a variable of the component's closure (`let uppy = null` in `upload-dropzone.js`), never on `this`.

**Alpine gotcha — a page listens on its own element, never on another component's root (caused a real bug):** an `x-on:` written on a component's root element is evaluated with THAT component's `this`, so a page's `x-on:upload-added="onUploaded(…)"` on the dropzone ran the page's method as the dropzone — the page's list refresh wrote into the dropzone's own `items`, and its rows turned into media rows. Put the listener on an element of the page around the component (the events bubble), and never give a shared component's state a name a page uses (the dropzone's rows are `uploads`, not `items`).

**Form gotcha — Enter in a search box inside a form sends the form (caused a real bug):** a channel's Add Ad keeps its picker's search box inside the `<form>` whose submit is Save, and a browser sends a form when Enter is pressed in any text box of it: somebody who typed a word and pressed Enter saved the ad with whatever tile was picked (found by hand in the full-app test round, 2026-10-02). A box inside a form that is not one of the form's own fields — a search, a filter — says what Enter does there (`@keydown.enter.prevent="loadPicker()"`: it searches at once), and `ChannelAdminTest` counts the requests to prove none is sent.

**Upload gotcha — `UploadedFile::fake()` believes the filename (weakens a real test):** a fake file's mime type comes from its NAME (`Illuminate\Http\Testing\File::getMimeType()`), while a real upload's comes from its BYTES (finfo). So `fake()->createWithContent('shell.jpg', '<?php …')` passes `mimes:jpg` in a test and is refused in production — the test proves nothing. To test what the server really does with a lie, build a real one: write the bytes to a temp file and `new UploadedFile($path, 'shell.jpg', 'image/jpeg', null, true)`, where the third argument is only what the CLIENT claims (`uploadWithBytes()` in `FileUploadAttackTest`). Keep `fake()` for size and for formats whose name and bytes agree — never for a VIDEO: the server measures a video from its bytes (**Upload limits**) and a fake has none, so it is refused. `Tests\Support\VideoFiles` builds real MP4 and WebM containers of any length and layout, and `VideoFiles::upload($bytes, $name, $reportedKilobytes)` can report a size larger than the bytes for the storage tests.

**Test gotcha — a session assertion between two requests empties the next page's errors (cost a debugging round, 2026-09-29):** this app keeps its sessions as JSON (`config/session.php`, `serialization`), so the session store turns the error bag into an array when it saves and back into a bag when it starts. `assertSessionHasErrors` (any `TestResponse` session assertion) starts it between two requests of one test, and the next request then marshals the same in-memory bag a second time — into an empty one — so the page after it shows no error although the redirect flashed it. A browser never meets it (every request loads the array afresh). A test that wants the error ON the page asserts the page alone, with no session assertion in between.

**Test gotcha — SQLite reads a column that does not exist as a word (hid a real crash):** Laravel quotes names with `"` on SQLite, and SQLite takes a double-quoted name it cannot find for a string. So `with('uploader:id,name')` passed every test, the uploader's name an empty string, while MySQL refused the query (users have `first_name` and `last_name`, no `name`): the TV App's Versions list would have answered 500 from its first upload (found 2026-10-15). A column named in `with('relation:…')`, `select`, `pluck` or `orderBy` is one the table has, and a test reads what that column feeds.

**Test gotcha — SQLite takes no locks (so an order of locks is tested by the statements sent):** a race the in-memory suite runs passes whatever order the locks are taken in. `tests/Support/TransactionStatements` (with `tests/Support/LocksShownGrammar`) records each transaction's statements with its locks written in as SQL comments, so a test checks the order MySQL relies on (**Hierarchy**, **Channels** (6)) and plays the other request at the moment it would commit; an integer key's id list is written into the SQL (`whereKey` → `whereIntegerInRaw`), so an expectation names the ids. A new path that locks rows is tested this way.

**Test gotcha — what only the browser decides is tested under Node too:** `Tests\Support\PageScript` runs a page's own `resources/js` module under Node from Pest, standing in for Alpine's magics, the toasts, a form on the page and an upload box, and routing its requests through the real axios. Each such test is seen failing on the old code first.

**Input gotcha — text that is not UTF-8 (caused real 500s):** a browser never sends it, but a request made by hand can, and such text passes every `string` rule — then broke whatever turned it into JSON (a 500 from the screen update, the screen listing's search and the channel create, "Malformed UTF-8 characters"), a MySQL row or a limiter's key. `RejectMalformedText` is PREPENDED to every route in `bootstrap/app.php` — the device API's too — and answers 400 before anything reads the query, the form, an upload's file name or the User-Agent the session keeps. Keep it first; never move it into a group.

**Input gotcha — a query parameter can be ANY shape (caused a real bug):** `?search[]=x` arrives as an array, and an array reaching a `like` clause, a `trim()` or a cache key is an "Array to string conversion" — which Laravel raises as an error, so the answer is a 500. It cost every listing in the panel and, worse, the device API's own limiter (`device-pair` keys on `?device_uuid`, and a limiter runs BEFORE the endpoint's validation, on a surface that is open on purpose). Wherever a word is read straight out of a request with no Form Request having checked its shape first, read it through `HandlesCrudData::plainValue()` — anything that is not one plain value reads as "not sent", which keeps a listing forgiving — or validate it (`['search' => ['nullable', 'string', 'max:255']]`, as both media pickers do). A route parameter its controller types `int` is bounded to what an int holds (`[1-9][0-9]{0,17}`, as the dashboard's invitation answers are in routes/web.php): a longer run of digits reached the parameter as a TypeError, a 500, where it should be a 404 (`HugeIdAttackTest`). And a regex that checks a whole value ends with `\z`, never `$`, which lets a closing newline through (`ChunkedUploads::typeOf`, `UploadController::number`).

**Search gotcha — `%` and `_` are LIKE's wildcards (caused a real bug):** a plain `where($column, 'like', "%{$search}%")` read "50%" as "50 and anything", so it found "Sale 500 off", "r_1" found "Bar21" and a lone `%` or `_` found every row (owner, 2026-10-15). Every search box's words go through **`whereContains($column, $search)`** / `orWhereContains` (`AppServiceProvider::registerSearchMacros`, on every query and Eloquent builder), which escapes `!`, `%` and `_` with `!` under its own `escape '!'`: MySQL's default escape, a backslash, means nothing to SQLite, and a typed backslash stays a backslash on both. A new search uses it, never a bare `like`, and joins `SearchAsTypedTest`'s lists. A list searched in the browser (Members, the editor's fonts) compares with `includes()`, which is literal already.

**Validation gotcha — a later rule still runs after `string` failed (caused real bugs):** Laravel runs every rule for an attribute unless the list begins with `bail`. A `name` posted as an array therefore failed `string` and then reached the closure that folds the name to compare it — `(string) $value` on an array, a 500 (`RoleController::validated`, `ChannelRequest`); and a `password` posted as an array failed `string` and then reached `current_password`, which hashes whatever it is handed — a 500 on EVERY big delete in the app (`Concerns\ConfirmsPassword`). All three now begin with `bail`. Any rule after a type rule that assumes the type held — a closure, `current_password`, `exists`, a custom Rule object — needs `bail` in front of it; a closure that only compares with `!==` (the organization-delete confirmations) is shape-proof and does not. The same applies one level down: a list validated as an `array` says nothing about what is INSIDE it, so a mapper typed `array $row` over `rules` blows up on `rules[]=x` until the elements are validated too (`PlaylistController::preview` now reuses the PUT's own `ruleRules()` for that).
